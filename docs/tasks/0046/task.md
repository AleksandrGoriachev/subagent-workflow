## Цель

Три прогона ворот (`task-red`, `task-verify`, `task-accept`) перестанут складывать длительности
независимых критериев: 0041 — 189 с на прогон при max(критерий) = 115 с, то есть 74 с лишних на
каждом прогоне. Критерии не делят состояние, поэтому их можно вести параллельно.

Первая редакция (0045) требовала «три критерия по 1,2 с уложились в 2,5 с». Внутри пула этот же
критерий соседствовал с другими, и на Windows цена запуска процессов (cmd.exe + node) сдвигала
измерение: 1,7 с в одиночку против 2,7–3,3 с рядом с тремя. Критерий краснел от загрузки машины, а
не от логики. Здесь он доказывает **перекрытие интервалов** — от нагрузки не зависит.

## Что не входит

1. Узкие наборы в `panel-older.mjs`/`engine-link.mjs` (WC-13) и литералы версий (WC-10) — отдельно.
2. Изменение набора критериев и формата вывода ворот.
3. Параллельный `setup`/`teardown` — они остаются последовательными.
4. Флаг `exclusive` (критерий без соседей) — отдельный follow-up: сначала нужен опыт эксплуатации пула.

## Инварианты

1. Порядок строк результата — как порядок критериев в `criteria.json` (ID не перепутаны).
2. Падение одного критерия не отменяет и не обрывает остальные; итоговый вердикт — как раньше.
3. `timeoutMs` критерия соблюдается для каждого.
4. Степень параллелизма: `WF_CRITERIA_PARALLEL` (число), по умолчанию 4; значение 1 — прежнее
   последовательное поведение.
5. Формат вывода ворот (`PASS/FAIL  C1  <мс>`, причины, итоговая строка) не меняется.
6. Непонятно — стоп и один вопрос. Догадываться запрещено.
