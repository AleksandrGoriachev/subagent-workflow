## Цель

Правила, которые сейчас живут только в брифах архитектора, должны стать частью контракта и проверяемой
политики. Критик посчитал: 7 приёмок = 3005 с, из них ворота 1092,8 с, ручные прогоны критериев
1103,7 с (≈980 — дубли ворот), 465,8 с убиты дедлайном обёртки 120 с. Правила в шаблоне убирают первые
две статьи потерь, политика в коде — третью (независимость приёмки).

## Что не входит

1. Печать подробного отчёта по критериям в stdout ворот (WC-24) — отдельным заданием.
2. Изменение схемы acceptance.json и подписи.
3. Изменение самих проверок.

## Инварианты

1. `task-accept`: при `risk >= medium` чтение отчёта исполнителя (`--report-read`) без явной причины
   (`--report-read-reason "<текст>`) — отказ до подписи, с рецептом; причина попадает в acceptance.json.
   При `risk = low` и без чтения поведение прежнее.
2. `actor.model` в записи — фактическая модель: `DSH_MODEL`, иначе конфиг `actor.model`, иначе `unknown`.
3. `spec/templates/task.md` §Среда: ворота только фоновым джобом или `run_code({ timeoutMs })`;
   ожидание порциями ≤90 с; ручной прогон критерия — не более одного и только если он <15 с; до старта
   ворот ≤120 с; отчёт исполнителя приёмщик не читает (кроме low) или называет причину.
4. Непонятно — стоп и один вопрос. Догадываться запрещено.
