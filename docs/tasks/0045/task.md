## Цель

Три прогона ворот (`task-red`, `task-verify`, `task-accept`) перестанут складывать длительности
независимых критериев: 0041 — 189 с на прогон при max(критерий) = 115 с, то есть 74 с лишних на
каждом из трёх прогонов. Критерии не делят состояние (временные корни изолируются в `runCheck`),
поэтому их можно вести параллельно, сохраняя порядок и вывод по ID.

## Что не входит

1. Узкие наборы в `panel-older.mjs`/`engine-link.mjs` (WC-13) и литералы версий (WC-10) — отдельно.
2. Изменение набора критериев, их команд и порядка вывода: поведение ворот снаружи не меняется.
3. Параллельный `setup`/`teardown`: они упорядочены по смыслу и остаются последовательными.

## Инварианты

1. Порядок строк результата — как порядок критериев в `criteria.json` (ID не перепутаны).
2. Падение одного критерия не отменяет и не обрывает остальные; итоговый вердикт — как раньше
   (красный, если хоть один не совпал с ожиданием).
3. `timeoutMs` критерия соблюдается для каждого; общий прогон не длиннее суммы, но и не короче
   самого долгого.
4. Степень параллелизма настраивается: `WF_CRITERIA_PARALLEL` (число), по умолчанию 4; значение 1
   даёт прежнее последовательное поведение.
5. Формат вывода ворот (`PASS/FAIL  C1  <мс>`, причины, итоговая строка) не меняется.
6. Непонятно — стоп и один вопрос. Догадываться запрещено.

## Среда

- Итерации: только затронутые файлы — `node spec/scripts/tests-for.mjs <изменённые пути>`;
  правки в `spec/scripts/**` гоняются точечно: `node spec/checks/parallel-criteria.mjs c1|c2|c3`.
- Полный набор — `node plugin/tools/test.mjs` — один раз, в конце (113 с); критерии задания его не требуют.
- Регресс правил пакета: `node spec/selftest.mjs`.

  увеличивать `timeoutMs` и не должен делить один `cwd`.
