# Анализ: канбан с распределением задач между воркспейсами (вместо сессий)

Кода в этой работе нет — только разбор возможности переноса модели
[dsh-kanban](https://github.com/VictorKozachek/dsh-kanban) с распределения задач между **сессиями**
на распределение между **воркспейсами**.

## 1. Что делает пример (факты, а не пересказ)

Источники: README, `AGENTS.md`, `KANBAN.md` репозитория (цитаты по состоянию на 20.11).

1. **Карточка = файл в репозитории проекта:** `.kanban/tasks/<ID>.md` со статусом, владельцем, ролью,
   веткой, расходом токенов и заметками. Доска — единственный источник правды, состояние не живёт в чате.
2. **Роль = сессия с пресетом** (`dispatcher`, `worker`, `reviewer`, `verifier`, `manager`). «Одна задача =
   один worktree = одна сессия = один набор файлов».
3. **Диспетчеризация — наряды в сессии того же хоста:** `sessionController.prompt` в режиме `queue`,
   состояние доставленных нарядов — `.kanban/.watcher-state.json` (ключ `<id>:<статус>:<updated>`).
4. **Воркспейс = рабочая директория.** Каждый git-worktree задачи открыт отдельным Workspace, поэтому у
   каждой роли «своя» сессия без ручной настройки — GUI группирует сессии по каталогу.
5. **Дочерние доски — только обзор.** Манифест `.kanban/children.json` (`bin/board-children.sh`, обход
   `--root`/`--depth`, внешние доски через `--board`), служба хоста `kanbanChildren` **read-only**;
   «наряды остаются у ролей дочерней доски» — то есть родитель видит, но не диспетчирует.

### Пределы, которые пример сам зафиксировал (`KANBAN.md`, раздел «Как устроена изоляция»)

- «One primary workspace root per session — policy resolves `SessionHeader.cwd`; extra writable roots are
  not part of `SandboxExecutionPolicy`» — **один корень на сессию**, дополнительных записываемых корней нет.
- Субагенты наследуют `cwd` родителя и сменить его не могут → фан-аут субагентами изоляции не даёт.
- «Запись — только внутрь своей директории, чтение — куда угодно»; `mkdir` рядом с проектом песочница отклоняет.
- `workspaceFiles` — read-only Remote: «The service exposes no mutation operation».
- Фид изменений не видит записи из bash/редактора → доска опрашивает файлы.

**Вывод по примеру:** это распределение работы *внутри одного воркспейса* (одного корня), где «исполнитель»
адресуется сессией. Между воркспейсами он умеет только *смотреть* (дочерние доски), но не распределять.

## 2. Чем «между воркспейсами» отличается от «между сессиями»

| Свойство | Между сессиями (пример) | Между воркспейсами (запрос) |
| --- | --- | --- |
| Единица владения | сессия | корень проекта (он же `SessionHeader.cwd` для её сессий) |
| Адресация задачи | `owner: <session-id>` | `workspace: <корень>` + роль/сессия внутри него |
| Транспорт наряда | `sessionController.prompt` | файлы в общем каталоге либо prompt в чужую сессию (см. §5) |
| Изоляция файлов | worktree на задачу | границы корня: чужой воркспейс писать нельзя |
| Гейты приёмки | общие для проекта | у каждого проекта свои (движок, политика, ключи, релизный путь) |
| Публикация | мерж ветки в проект | релиз/деплой *своего* проекта, своим узлом |
| Аудит | `.kanban` и state-файлы | + межпроектный след (сейчас — письма в `coordination`) |

Ключевое: при распределении между воркспейсами нельзя «назначить задачу на сессию» — можно только
назначить **проекту**, а кто внутри него возьмёт работу, решает сам проект. Иначе координатор пробивает
границу изоляции и обходит гейты проекта.

## 3. Что уже есть в нашей среде (факты)

1. **Зарегистрированные корни.** Панель (`/workflow/api/status`) знает 5 корней: `default-workspace`,
   `dsh-project-graph`, `ws-school-app`, `split-optimizer`, `reach-proxy`; спавн узлов ограничен
   разрешённым списком (проверено: корень пакета отклоняется `root-not-allowed`).
2. **Сессии группируются по каталогу** — в `~/.dsh/sessions` отдельный каталог на каждый корень
   (10+ проектов).
3. **Живость уже решена файлами:** `coordination/presence/<workspace>.json` (`version, workspace, sessionId, at`)
   — обновляется каждой стороной.
4. **Транспорт между сторонами уже есть:** `coordination/threads/exchange` + `dsh-exchange/1` (шапка,
   `Session`, `Reply-To`), инструменты `exchange-inbox` и `check-exchange` (счётчик наших/входящих, чей ход).
5. **Панель уже показывает задачи по корню** (`/workflow/api/tasks?root=…`), то есть «доска воркспейса» —
   не новость; её данные — `docs/tasks/<id>` проекта.
6. **Свидетельства запуска** хранятся по хешу корня (`runs/<sha256(root)[:12]>/launches.jsonl`) — адресация
   «по воркспейсу» в движке уже есть.
7. **Ограничение, которое мы соблюдаем:** без указания не входить в чужой воркспейс (ни читать, ни
   запускать); переписка — через `coordination`. Это придётся сохранить и в канбане.
8. **Версии движка у проектов разные** (структура обновилась на 2.6.86; не все проекты равны), значит
   межпроектный протокол должен быть версионно-нейтральным (файлы + явные поля), а не «вызовом API чужого движка».

## 4. Три варианта архитектуры

### A. Центральная доска-шина (карточки вне репозиториев)

Карточки живут в общем каталоге (`coordination/kanban/<ID>.md`), каждый воркспейс держит лёгкого
наблюдателя, наряды — файлы в `coordination/kanban/inbox/<workspace>/`.

- Плюсы: один источник правды, координатор видит всё, не нужен доступ на запись в чужие репозитории,
  работает при разных версиях движка, ложится на уже существующий `coordination`.
- Минусы: карточка оторвана от кода (нет связи с веткой/коммитом проекта), нужен явный контракт
  «кто и чем доказывает готовность», риск второй правды рядом с `docs/tasks`.

### B. Доски живут в проектах, родитель — сводка и планировщик

Карточка создаётся **в проекте-исполнителе** (`docs/tasks/<id>` или `.kanban/tasks/<id>`), родитель
держит только распределение: «проект X, задача Y, приоритет, срок, ссылка». Обзор — как `children.json`
в примере, но **с доставкой наряда**, а не только чтением.

- Плюсы: задача там, где код и гейты; приёмка и релиз — штатные, чужие границы не пробиваются;
  совпадает с нашей моделью «письмо в обмен, а не запись в чужой воркспейс».
- Минусы: нужен манифест проектов (реестр корней) и двусторонняя синхронизация статуса (кто хозяин
  статуса — проект-исполнитель); «взять в работу» требует доставки наряда внутрь проекта.

### C. Гибрид: карточка-источник у исполнителя + зеркало в родителе

У исполнителя — рабочая карточка и все доказательства; в родителе — зеркало с хешем содержимого и
ссылкой. Статус читается из источника, зеркало нужно только для обзора и планирования.

- Плюсы: нет двойной правды (зеркало производное), родитель не пишет в чужой проект.
- Минусы: нужен детерминированный рендер/хеш зеркала и правило «зеркало устарело».

**Сравнение по критериям**

| Критерий | A. Шина | B. Доски в проектах | C. Гибрид |
| --- | --- | --- | --- |
| Не пробивает границы воркспейсов | да | да | да |
| Задача рядом с кодом и гейтами | нет | да | да |
| Единый источник правды | да | да (у исполнителя) | да (у исполнителя) |
| Работает при разных версиях движка | да | да | да |
| Требует правок DSH/плагинов | минимум | доставка наряда | доставка наряда |
| Сложность реализации | низкая | средняя | высокая |

## 5. Что можно сделать на существующих механизмах, а что требует проверки

**Уже возможно (без кода плагина):**
- реестр корней — из `/workflow/api/status` (`roots`) и `coordination/presence`;
- карточка-файл со схемой (`id, project, role, status, priority, owner_session, lease_until, gates, evidence`);
- транспорт наряда — файл в `coordination/kanban/inbox/<workspace>/` + отметка «доставлено» (как
  `exchange-inbox` уже делает для писем);
- лизинг — `presence/<workspace>.json` + TTL: если `at` старше TTL, работы у проекта нет и задача
  возвращается в очередь (аналог `STALE` у `job.mjs`, который у нас уже есть);
- обзор — панель уже читает задачи по `root`.

**Требует проверки (неподтверждено):**
- Можно ли из плагина/узла направить prompt в **сессию другого воркспейса** по id (в примере
  `sessionController.prompt` работает с сессиями своего хоста; ограничение «один корень на сессию»
  делает контекст сессии привязанным к каталогу). Если нельзя — доставка наряда остаётся файловой,
  и это надо принять как проектное решение, а не как недоделку.
- Ведёт ли DSH учёт «сессия ↔ воркспейс» в публичном API (для адресации «проект → свободная сессия»).

## 6. Риски

1. **Двойная правда.** Карточка в родителе и `docs/tasks` в проекте — неизбежный конфликт, если не объявить
   хозяина статуса (предлагаю: хозяин — проект-исполнитель, родитель только планирует).
2. **Обход гейтов.** Задача, назначенная «напрямую исполнителю в чужом проекте», обходит его приёмку,
   ключи и релизный путь. Правило: любой кросс-проектный наряд обязан пройти гейты проекта-исполнителя.
3. **Гонки и зависшие лизы.** Без TTL задача навсегда «в работе»; нужен возврат в очередь и журнал.
4. **Проекты с разными версиями движка.** Протокол должен быть файловым и версионно-нейтральным.
5. **Безопасность.** Кросс-проектный координатор не должен читать секреты и писать в чужие репозитории;
   наш императив «без указания не входить» остаётся.
6. **Аудит.** Нужен append-only журнал переходов (у нас уже есть `gates.jsonl` и письма — их можно взять
   за образец, но не смешивать).

## 7. Оценка осуществимости

- **Вариант A** — высокая: только файлы и существующие инструменты координации; пилот за один шаг,
  но карточки будут жить «рядом» с задачами проектов.
- **Вариант B** — высокая по механике (реестр корней + манифест + инбоксы) и **средняя по доставке
  наряда**: если prompt в чужую сессию недоступен, проект забирает наряд при следующем обращении к
  инбоксу (как мы читаем письма) — это рабочий, хоть и не мгновенный путь.
- **Вариант C** — низкая ценность при высокой сложности, пока не доказана нужда в идеальной синхронизации.

**Рекомендация:** начинать с **B в файловом исполнении** (карточка у исполнителя, манифест проектов,
инбоксы и presence-лиз), а вопрос «prompt в чужую сессию» решать отдельно, как улучшение доставки.

## 10. Модель заказчика: канбан поверх структуры из 4 воркспейсов

### 10.1 Как это устроено (фиксация постановки)

Реалм: **ТВ Консоль → Прокси (сборка данных) → Оптимизатор (процессинг) → Прокси (очистка) → Консоль**.
Отладка серии долгая — это и есть главная боль.

Воркспейсы: 1) архитектурный; 2) консоль; 3) прокси; 4) оптимизатор. У 2–4 свои репозитории. У каждого
воркспейса есть связь со всеми воркспейсами реалма. Задача заводится и обсуждается **в архитектурном**
воркспейсе; архитектор вешает задания для трёх воркспейсов разработки; те согласуют между собой стандарты
обмена, согласуют декомпозицию и выполняют задачу, передавая состояния архитектору. **Всё движение
канбана — в рамках воркспейса архитектора.**

### 10.2 Что в модели сильно

1. **Один хозяин доски.** Распределение и приёмка стадий в одном месте — нет «трёх правд» о том, что важно.
2. **Задача начинается с обсуждения, а не с кода.** Контракт и декомпозиция до работ — ровно то, чего не
   хватало в отладке серии.
3. **Разделение владения:** архитектор — что и зачем, исполнители — как и чем докажут. Совпадает с нашей
   моделью контракта и приёмки.

### 10.3 Три места, где модель упрётся (по фактам DSH и структуры)

1. **Запись только внутрь своей директории.**
   Корень песочницы сессии = её `cwd`, дополнительных writable-корней нет (`KANBAN.md`, раздел об изоляции).
   Значит воркспейсы 2–4 **не смогут писать карточки на доске архитектора**. Они могут их *читать*
   (чтение — куда угодно) и сообщать о переходах письмом/инбоксом. Вывод: переход состояния — **двухфазный**:
   исполнитель *предлагает* («готово, доказательства такие»), архитектор *применяет* переход на доске.
2. **Доставка наряда в чужую сессию не подтверждена.**
   `sessionController.prompt` работает с сессиями своего хоста; сессии привязаны к каталогу. Пока не доказано
   обратное, наряд в воркспейс 2–4 доставляется **файлом** (инбокс + отметка доставки), как письма обмена.
3. **«Связь со всеми» ≠ право писать всем.** У нас действует императив «без указания не входить в чужой
   воркспейс». Значит связь — это обмен *сообщениями* через общий `coordination`, а не прямой доступ к файлам
   и сессиям соседа.

### 10.4 Что я бы уточнил в модели

**а) Два уровня карточек, один хозяин.**

- **Эпик (доска архитектора)** — задача реалма: описание, затронутые воркспейсы, контракты, стадии.
- **Наряд (доска архитектора, вид «по воркспейсу»)** — кусок работы для конкретного воркспейса: что сделать,
  какой контракт соблюсти, что предъявить, от кого зависимости.
- **Исполнительская карточка (в своём репозитории)** — как он это делает: `docs/tasks/<id>` с его гейтами.
  Хозяин статуса — исполнитель; на доску архитектора уходит **зеркало** (состояние + хеш доказательства).

Это снимает конфликт «карточка на доске архитектора vs карточка в проекте» и сохраняет правило «все движение
канбана — у архитектора»: у него двигаются **наряды и эпик**, а внутри проекта живёт исполнение.

**б) Матрица «кто что пишет».**

| Объект | Где | Пишет | Читают |
| --- | --- | --- | --- |
| Эпик | доска архитектора | архитектор | все |
| Наряд | доска архитектора | архитектор (переход — по предложению исполнителя) | все |
| Контракт обмена (схема+версия) | `coordination/contracts/` | архитектор после согласования | все |
| Исполнительская карточка | репозиторий проекта | проект | архитектор (чтение) |
| Квитанция/доказательство | письмо в обмен + инбокс доски | проект | архитектор |

**в) Контракт обмена — обязательный артефакт, а не договорённость в чате.**
Серия консоль→прокси→оптимизатор ломается на стыках, поэтому «стандарты обмена» должны быть файлом с версией:
имя, версия, схема полей, примеры, кто владеет, кто утвердил. **Изменение — только новой версией**, как у нас
с якорями и пресетами: смена контракта без версии — это и есть та самая «долгая отладка».

**г) Отладку серии снимают не карточки, а сценарии.**
Главная боль — прогон всей цепочки. Поэтому в эпике нужен **сценарий**: пошаговый эталон (вход консоли →
что должен получить прокси → что оптимизатор → что вернулось), с сохранёнными входами/выходами стадий и
проверкой на каждом стыке. Тогда «отладка» — это сравнение с эталоном на стыке, а не ручной прогон серии.
Каждая стадия владеет своими фикстурами, эпик — эталонной серией.

### 10.5 Состояния наряда и кто двигает

| Состояние | Кто применяет | Условие входа |
| --- | --- | --- |
| `proposed` | архитектор | задача заведена, воркспейсы назначены |
| `agreed` | архитектор | согласованы контракт обмена и декомпозиция (письма от 2–4) |
| `in-progress` | архитектор (по акцепту исполнителя) | воркспейс взял наряд, есть лиз |
| `integration` | архитектор | стадия предъявила результат на стык (фикстуры/логи) |
| `accepted` | архитектор | доказательства приняты: гейты проекта + проверка стыка |
| `done` | архитектор | все наряды эпика приняты, эталонная серия зелёная |
| `blocked` / `needs-decision` | исполнитель предлагает, архитектор применяет | стык не сходится, контракт неясен, нужна смена версии |

Лиз: `owner = воркспейс`, `lease_until` в карточке, продление — presence-файлом (как `coordination/presence`).
Просрочен → возврат в `agreed`, журнал перехода обязателен.

### 10.6 Остаточные риски именно этой модели

1. **Архитектор — узкое место и накопитель контекста.** Все переходы через него: при 4 воркспейсах это ок,
   при 10 — очередь. Мера: переходы `in-progress` и `blocked` применяются по квитанции автоматически,
   архитектор решает только `accepted`/`done`.
2. **Три исполнителя согласуют стандарт между собой.** Согласование может не сойтись — нужен таймаут:
   нет согласованного контракта к сроку → `needs-decision` архитектору, а не тихое расхождение.
3. **Двойная правда зеркала.** Зеркало на доске обязано нести хеш доказательства; расхождение — сигнал,
   а не повод «подождать».
4. **Циркулярные зависимости** (консоль ждёт прокси, прокси ждёт оптимизатор, оптимизатор ждёт контракт
   консоли) — в нарядах нужно явное `blocked_by` и правило «первым фиксируется контракт, потом код».
5. **Дороговизна эталонной серии.** Прогон реалма тяжёлый: сценарии должны быть многоуровневыми (стык пары
   стадий / вся серия), иначе каждый переход будет требовать полного прогона.

### 10.7 Вердикт

Модель **осуществимым образом ложится на структуру** при трёх поправках: (1) карточка-источник у исполнителя,
на доске архитектора — наряд и зеркало; (2) переходы состояний двухфазные — предлагает исполнитель, применяет
архитектор; (3) стандарт обмена — версионированный файл-контракт, а отладка серии — эталонный сценарий эпика.
Так «всё движение канбана у архитектора» сохраняется, а границы воркспейсов и гейты проектов не пробиваются.
