# Модель угроз: факты, подписи, доказательства

Версия 0.1 · 2026-11-11 · относится к `spec/` (движок ограничений) и `docs/facts/`.

## 1. Что мы защищаем

| Актив | Почему важен |
| --- | --- |
| Факты решений (`evidence`, `judgment`, `accept`) | по ним движок выносит вердикт; подделка = ложная приёмка |
| Цепь фактов (`prev`) | делает удаление и перестановку видимыми |
| Подписи решений | доказывают, что факт записал владелец ключа, а не кто угодно |
| Контракт задачи (`task.md`, `acceptance.json`) | задаёт запреты, план и привязку seal |
| Запечатанный тест | проверка, которую исполнитель не видит в своём дереве |

## 2. От кого защищаемся

| Актёр | Возможности | Защищено? |
| --- | --- | --- |
| **A1. Агент, который ошибается** | пишет факты через наши инструменты, путает прогоны, теряет шаги | да: C1–C10, цепь, манифест |
| **A2. Агент, который хитрит** | правит дифф, подкладывает старые доказательства, обходит запреты путями | да: run-scoping, канонизация путей, конфликт гейтов, подписи |
| **A3. Оператор с доступом к ФС** | правит `task.md`, пересобирает факты, запускает `--repair`/`--rebuild` | **частично**: подписанное не карантинится, пересборка отказывает при подписанном sealed, но владелец ключа может подписать заново |
| **A4. Злоумышленник с ключом** | владеет `agent-facts.key.pem` | **нет** — это уровень HSM/отдельного пользователя ОС, вне текущей модели |

## 3. Что закрыто механизмом (проверяется тестами)

| Угроза | Механизм | Тест |
| --- | --- | --- |
| Доказательства от другого прогона | `run` из `accept`, cross-run → C10 | `adversary-regressions` c2 |
| Конфликт гейтов (pass и fail) | конфликт до политики → C5 fail | `adversary-regressions` c3 |
| Обход запретов путями | `canonicalPath` (dots, absolute, escaped) | `adversary-regressions` c1, `mutation` |
| Подмена факта после записи | подпись по каноническому телу с `prev` | `fact-sign` c1–c2 |
| Перенос факта в другую цепь/задачу | `prev` + домен задачи в подписи | `fact-sign` c2, `mutation` |
| Чужой ключ | `keyId` в теле, сверка с `acceptors.json` | `fact-sign` c3 |
| Неподписанное решение | проверка по умолчанию → C10 fail | `fact-sign` c4, `mutation` |
| Удаление неудобного доказательства | цепь + подписи + манифест | `mutation` (10+ кейсов) |
| seal без привязки к контракту | `acceptance.taskFileSha256` обязателен | `sealed-run` c1–c4 |
| «Тихий выход» CLI на коротком пути Windows | `isMainModule` (realpath) | `pipe-free` c1–c5 |

## 4. Остаточные риски (приняты осознанно, не «дыры» недосмотра)

| Риск | Почему принят | Что нужно, чтобы закрыть |
| --- | --- | --- |
| Владелец `agent-facts.key.pem` может подписать любое решение | ключ лежит на той же машине, где идёт работа | ключ под отдельным пользователем ОС/HSM, подпись через сервис |
| `--rebuild` и `--repair` — операции администратора | администратор и так может менять состояние; след остаётся в git и карантине | внешний журнал операций, append-only вне машины |
| Sealed-тест читаем (L1) | одна учётная запись ОС | отдельный пользователь/контейнер (L2) |
| Мутационный набор конечен | он доказывает классы отказов, не все сценарии | расширять по каждой новой находке (как сейчас) |
| `task-accept` пока не вызывает движок | P2 не начат | интеграция и откат (P2) |

## 5. Инварианты, которые обязаны держаться

1. Ни один факт-решение не принимается без сходящейся подписи зарегистрированного ключа.
2. Все доказательства вердикта относятся к одному `run`, названному в `accept`.
3. Добавление лишнего факта не улучшает вердикт (монотонность).
4. Удаление любого обязательного факта делает вердикт `rejected`.
5. `not-applicable` означает «обязанности нет», а не «доказано».

## 6. Как проверять модель (а не код)

- новое ревью начинается с вопроса: «какой актёр из §2 и какое обещание из §3/§5 ломается?»;
- если сценарий требует возможностей A4 — это не находка, а предложение о смене уровня;
- каждая новая находка обязана превратиться в тест в `plugin/test/` и, при необходимости, в строку §4.
