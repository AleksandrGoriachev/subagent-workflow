# ANCHORS — семантические якоря контура workflow

Дата фиксации: 2026-11-09. Контур на фиксации: движок 2.6.58, панель 0.9.27, DSH 0.2.2-rc.1.

**Мета-правило чтения документа.** Якорь действует ровно настолько, насколько его проверка была запущена недавно и на развёрнутой копии. Список с непрогнанными проверками — это декларация, а не гарантия. Прогон в исходнике — репетиция; вердиктом считается прогон на том, что реально работает.

Формат строки: правило — что оно не разрешает (граница) — чем проверяется — статус (автомат / полуавтомат / в работе) — последнее подтверждение и версии.

## 1. Зоны правок и единственный путь

Правило: исполнитель меняет только свою зону. Чужая зона — только письмом в `coordination/threads`. Наш собственный выпуск — только через `commit.ps1` и `release-publish`.
Граница: не запрещает structure менять свой репозиторий; запрещает обходить её процесс «по-тихому».
Проверка: `guard-acceptance` (обход ворот) — автомат. Таблица зон: наш, их, обмен.
Статус: автомат. Подтверждено 2026-11-08, 2.6.55–2.6.58 (коммиты через commit.ps1, их дерево чисто после отката).

## 2. Проверяемый результат до работы

Правило: нельзя начинать исполнение, пока критерии не зафиксированы в контракте.
Граница: не запрещает пересматривать критерии — только делает это отдельным согласуемым изменением, а не правкой «по ходу».
Проверка: `task-lint` (W: контракт без наблюдаемых критериев → ERROR), `relock-policy` (правка после красного — по правилу).
Статус: автомат. Подтверждено 0052/0050, живьём на 0150/Unnamed — в наших задачах повторно не замечено.

## 3. Каждый факт — с источником; кэш не выдают за свежесть

Правило: версия, модель, состояние папки, версия релиза — всегда с указанием, откуда факт. `unknown` допустим, только если источник проверяли и его нет. Кэш — с временем и пометкой.
Граница: не запрещает оптимизм, запрещает выдачу предположений за данные.
Проверка: `model-source` (модель приёмника с источником), `release-check` (`checkedAt`, `latest` из кэша только с пометкой).
Статус: автомат. Подтверждено 2026-11-08 (2.6.51–2.6.58, WC-25/WC-65).

## 4. Отказ называет причину и следующий шаг

Правило: любой отказ, доступный пользователю, содержит что упало, где, и безопасный следующий шаг.
Граница: не требует раскрытия внутренних деталей (пути, секреты) — часть «где» может быть уровнем «движок/панель/сеть».
Проверка: `release-check` c4 (причина + «последняя удачная проверка»), `plugin-update` (тексты hint), `fail`-тексты в клиентах.
Статус: автомат (частично — полуавтомат по быту; покрываем по файлам). Подтверждено 2026-11-08 (WC-64/65/66).

## 5. Контракт до красного; как красный появился — это и есть результат

Правило: критерий без красного прогона подозрителен — он не доказал, что проверял.
Граница: не запрещает писать код до критериев в дешёвых правках; претензия в том, что приёмки без красного требуют нестандартной оговорки.
Проверка: `gates-journal` (вердикты ворот считаемы), `relock-policy`.
Статус: автомат. Подтверждено 2.6.18+ (0050/0051).

## 6. Тест проверяет разговор, а не только ответ

Правило: для сетевого кода тест обязателен на URL/метод/заголовки + на отказ (мок обязан отвергать: 415/403), а не только на успешный ответ.
Граница: не ограничивает число тестов — ограничивает их качество.
Проверка: `network-contract` c1–c4 + `outgoing-headers` c1–c4.
Статус: автомат. Подтверждено 2026-11-08 мутационным тестом (дефект 415 ломает раннер; после отката — зелёно).

## 7. Общий модуль — проверка всех вызывающих

Правило: правка общего модуля фиксирует список вызывающих и ожидания каждого; у каждого — тест.
Граница: не запрещает менять общие модули; запрещает менять «вслепую».
Проверка: **в работе (WC-69)** — сейчас покрывается только дисциплиной, не машиной.
Статус: в работе (WC-69).

## 8. Дефект → гейт → доказательство, что гейт ловит

Правило: после проскочившего дефекта добавляется гейт **на класс** и мутационное подтверждение, что он падает на старом поведении.
Граница: не запрещает точечные фиксы; требует, чтобы точечный фикс сопровождался классовым, где класс уместен.
Проверка: демо 2026-11-08 (415 → network-contract падает, фикс возвращает зелёный).
Статус: автомат (по случаю каждого дефекта; ручной шаг, но короткий).

## 9. Выпуск: draft → smoke → publish → анонимная проверка

Правило: публикация возможна только при свежей квитанции приёмки на реальном проводе; после публикации — та же приёмка без токена (как увидит потребитель).
Граница: не ограничивает частоту выпусков; ограничивает порядок.
Проверка: `release-publish` c4 (без квитанции отказ; со свежей квитанцией — публикует), `release-smoke` (tag, ассеты, sha, VERSION в tarball).
Статус: автомат. Подтверждено живьём 2.6.57/2.6.58, анонимная приёмка обеих — OK.

## 10. Три состояния письма — три разных факта

Правило: «лежит» ≠ «прочитан» ≠ «доставлен с пробуждением». Ответ — с `Reply-To` и `Session`; гейт-отказ — с веткой, а не тишиной.
Граница: не требует мгновенной доставки (ящик может ждать), требует честного статуса.
Проверка: журнал `exchange-decisions.jsonl` (полуавтомат — читаем и сверяем); счётчик `exchangeAttention` для заявок.
Статус: полуавтомат. Подтверждено 2026-11-08 (gate:invited 15:33 → delivered 16:21; после 16:20 отказов нет).

## 11. Отчёт говорит только доказанное; флейк — не вердикт

Правило: зелёный — значит перечисленные проверки пройдены (и где именно они были прогнаны). Сбой по среде (EPERM, rename-флейк, 504 на одном прогоне) не PASS и не FAIL — повторить или пометить средой.
Граница: не запрещает качественные выводы; запрещает делать их шире доказанного.
Проверка: `report-honesty`; по практике дня — анонимный smoke, развёрнутая копия.
Статус: полуавтомат. Проверка выбирает честность; иначе — свод правил, который обязан читать человек.

## 12. Ожидания — сторожем, а не сном

Правило: инструмент не ждёт долго внутри себя; тяжёлые прогоны — через `job` (start/wait).
Граница: не запрещает короткие ожидания; задаёт порог (160 с и больше — уже через job), при котором это обязано быть.
Проверка: `job-runner`; `pipe-free` — как близкие технические ограничения среды.
Статус: автомат. Подтверждено живьём (084/0053/0072).

## Порядок пересмотра

При каждом проскочившем дефекте: либо обновить существующий якорь, либо добавить новый (с проверкой) — но держать объём в 12 ± 1. Перечитывать список при каждом крупном выпуске; поправлять даты подтверждения только после реального прогона.

## Единая версия и утверждение

Машинный источник истины — `docs/anchors.json`. `ANCHORS.md` — человекочитаемое отражение того же набора: правится только через `anchors.json`, иначе редакций станет две.

Утверждение фиксируется подписью в `anchors.approval.json`: `{ hash: sha256(anchors.json), by: «пользователь + coordinator», at, signature, panel }`. Любая правка якорей аннулирует утверждение до переподписания — это и есть запрет на тихий дрейф.

Якоря со `scope: both` живут одной редакцией в папке обмена (`coordination/ANCHORS-both.json`, две подписи). Копий по сторонам не бывает.

## Напоминания о возрасте якорей

Критик в ежедневном отчёте приводит таблицу «якорь — возраст подтверждения — статус» и напоминает координатору о перепроверке. Порог свежести (`anchors.json → freshness`):

- `auto` — 14 дней или 5 релизов;
- `semi` — 30 дней или 10 релизов;
- `inWork` — без срока, но виден в отчёте как незакрытый.

За 7 дней до порога критик предупреждает заранее. Механическую сторону (неподписанный или протухший якорь валит релиз) держит `spec/checks/anchor-freshness.mjs` (WC-70, в работе) — рекомендация критика не заменяет эту проверку.
