# Стоп-линия: три задачи с внешними критериями

Дата: 2026-11-11. Автор критериев и приёмочных чеков — **workflow** (не исполнитель).
Исполнитель кода — structure. Приёмка — исполнением на стороне workflow.
Основание: внешний аудит `docs/AUDIT-dsh-project-graph-2026-11-11.md`.

## Правила стоп-линии (обязательны для всех трёх)

1. Критерии фиксируются **до** начала кода и не меняются исполнителем; правка критериев — только через exchange.
2. Внешние чеки живут в нашем репозитории: `spec/checks/stopline/t1..t3`. Исполнитель может гонять их локально, но доказательством считается прогон на нашей стороне.
3. Провал любого чека блокирует приёмку. Зелёные логи исполнителя доказательством не являются.
4. Новые фичи не входят. Только перечисленные ниже изменения; всё остальное — в очередь.
5. Приёмка идёт на чистом клоне: чеки не должны требовать файлов, созданных исполнителем после фиксации.

## T1. Регрессионный гейт в приёмке

**Проблема:** `task-regress.mjs` написан (249 строк), но в `task-accept` — 0 упоминаний; вне e2e регрессии не перезапускаются.

**Что сделать:**
- подключить `task-regress` в `task-accept` после `verify`, до `accepted`;
- провал регресса — отказ приёмки с перечнем упавших задач и критериев;
- ночной запуск регресса (расписание или общий прогон), не только e2e;
- **до включения гейта** — baseline-прогон и список уже известных провалов.

**Критерии (внешний чек `t1-regress-gate.mjs`):** `task-accept` вызывает регресс; провал блокирует приёмку; вне e2e есть запуск, который зовёт регресс.

**Не входит:** новые проверки, изменение существующих чеков, UI.

## T2. Граф без потерь + активация в своём воркспейсе

**Проблема:** `buildStructure` (api.js:2327–48) собирает whitelist и перезаписывает файл — теряются `prompt`, `anchors`, координаты, расписание, привязки сессий. Позиции/папки панели живут в том же `graph.json` (54 коммита, 26 ручных; `e60547c` «вернуть folder-5»). Активация создаёт сессию в `Temp\dsh-spawn-*` — координатор падает (журнал 11.11 07:38).

**Что сделать (минимально, fail-closed):**
- `buildStructure` сохраняет неизвестные поля **или отказывается** перезаписывать файл;
- позиции/папки/привязки — отдельный файл состояния, не конфиг;
- `add/updateNode` не откатывают чужие новые байты (CAS по rev/hash);
- активация отклоняет сессию, созданную не в воркспейсе узла, с понятной причиной.

**Критерии (внешний чек `t2-graph-noloss.mjs`):** сборка не whitelist; состояние панели отделено; spawn проверяет воркспейс.

**Не входит:** полный рефакторинг `api.js` (7726 строк) — это P2, отдельной задачей.

## T3. Одна правда политики якорей + чистый реестр

**Проблема:** A8 в `docs/anchors.json` обещает «ревьюер без consumes — отказ», а `role-policy.js:143–60` (0206) раздаёт «все auto». В реестре 11 фантомных `open` — дубли принятого.

**Что сделать:**
- A8 либо переутвердить под 0206 (убрать claim об отказе), либо вернуть отказ в `role-policy`;
- `role-policy` — единственный исполняемый источник, манифест якорей ссылается на него;
- тесты ролей перевести с legacy-фикстур `active/inWork` на auto-корпус;
- реестр: фантомные `open` → `cancelled` со ссылкой «→ NNNN».

**Критерии (внешний чек `t3-policy-truth.mjs`):** нет противоречия A8 ↔ role-policy; `rolePolicy` экспортируется; фантомных open — 0.

## Порядок и приёмка

1. T1 (1 день) → baseline + проводка;
2. T2 (2–3 дня) → fail-closed первым коммитом;
3. T3 (1 день) → после T2, чтобы не смешивать политику с данными.

Приёмка каждой задачи: прогон внешнего чека на нашей стороне + прогон регресса + независимый ревьюер диффа (worker-2). Метрики через 7 дней: M1 (100% приёмок с regress), M2 (0 правок graph.json вне задач), M3 (доля кодовых коммитов ≥50%, длина цепочки переделок ≤2).
