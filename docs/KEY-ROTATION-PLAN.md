# План ротации ключа приёмщика (`agent-judge`)

Версия 0.2 · 2026-11-11 · **выполнено** по решению заказчика («нужен новый приватный ключ, раз старый потерян»).

## 1. Факт

В `docs/subagent-workflow/acceptors.json` есть публичный ключ `agent-judge` с отпечатком
`d8b2d1bad69e228a`. Приватного ключа, соответствующего ему, на диске нет: единственный
найденный (`~/.wf-keys/agent-judge.key.pem`) даёт отпечаток `e4b77f4c2b9f9a8a`.

Следствие: подписи в исторических `acceptance.json` этим ключом **повторно не проверяются**.
Сами приёмки от этого не «исчезают» — они лежат в git и датированы, но криптографически
подтвердить авторство сейчас нечем.

## 2. Что предлагается

1. Сгенерировать новую пару ключа приёмщика (ed25519), приватную часть держать вне репозитория
   (`~/.wf-keys/<repo>/agent-judge.key.pem`), публичную — в `acceptors.json`.
2. В `acceptors.json` добавить запись с новым отпечатком и полем `activeFrom` (дата/время),
   старую запись сохранить с `retiredAt` и пометкой `legacy: true`.
3. Все подписи, сделанные **до** даты ротации, при проверке считать `legacy`: они не проходят
   криптопроверку, но помечаются как исторические, а не как подделка.
4. Новые приёмки подписываются только новым ключом. Проверка «подпись сделана ключом,
   действовавшим на дату приёмки» — по `activeFrom`/`retiredAt`.

## 3. Что нельзя делать молча

- менять публичный ключ в `acceptors.json` без записи о ротации: тогда старые подписи станут
  «подделкой» в глазах проверок, хотя они честные;
- подписывать новые приёмки тем же `keyId` со старым отпечатком — это смешает эпохи.

## 4. Цена ошибки

Если ротацию сделать без `legacy`-пометки, `task-check-acceptance` и движок начнут краснеть на
исторических задачах. Это ложная тревога, которая обесценивает проверки — ровно то, чего мы
избегаем в модели угроз (§4: остаточные риски должны быть названы, а не замаскированы).
