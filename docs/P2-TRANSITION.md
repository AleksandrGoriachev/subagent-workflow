# Переход P2b → P2c: когда включаем блокировку

Версия 0.1 · 2026-11-11 · решение по данным, а не по ощущению.

## 1. Что уже есть

`task-accept` пишет `docs/tasks/<id>/engine-shadow.json`: вердикт движка, статус приёмки,
`agree`, полный отчёт по C1–C10. Тень не блокирует и не меняет приёмку.

Сводка: `node spec/scripts/engine-shadow-summary.mjs --workspace .` — считает расхождения и
группирует их по ограничениям. Шаг `SHADOW` в selftest падает, если есть DIFF.

Текущее состояние: корпус 5/5, расхождений 0.

## 2. Критерий включения блокировки (P2c)

Блокировка включается, когда выполнены **все** условия:

1. **Не меньше 5 реальных приёмок** после включения тени (не корпус, а живые задачи).
2. **Ноль расхождений**, либо каждое расхождение объяснено в `DATA-MODEL-MIGRATION-STATE.md`
   с указанием, какая сторона была неправа (движок или приёмка) и что исправлено.
3. **Ни одного `not-checked`** по причинам, которые мы не понимаем: «нет ключа», «не конвертируется»,
   «нет журнала» — допустимы только как явно принятые ограничения в модели угроз §4.
4. **Откат проверен**: выключение `engineShadow`/`engineGate` возвращает прежнее поведение
   без правки кода (флаг в конфиге, не пересборка).

## 3. Как выглядит включение

- `engineGate: true` в `workflow.config.json` (по умолчанию `false`);
- при `engineVerdict === 'rejected'` приёмка **падает** с кодом 1 и печатает, какое ограничение нарушено;
- `--force` остаётся, но пишет причину в `acceptance.json` (`engineOverride`) — обход виден;
- тень продолжает писаться всегда, чтобы было видно, что было бы без блокировки.

## 4. Что считается регрессией

- любая задача, которая была `accepted` движком, стала `rejected` без изменения фактов — регрессия движка;
- задача, где приёмка и движок разошлись, а объяснения нет — блокирует P2c.

## 5. Откат

1. `engineGate: false` (или `WF_ENGINE_GATE=0`) — приёмка снова только по старым правилам.
2. Тень выключается `engineShadow: false`.
3. Код не удаляется: старые 59 проверок остаются за шимом до истечения срока (2 задачи).
