# Спецификация данных и ограничений (v0.1)

Дата: 2026-11-10. Основание: разговор заказчика про реляционную/функциональную парадигму:
данные сами доказывают корректность, проверки — предикаты над фактами, а не слои суждений.
Статус: черновик на ревью (адвокат дьявола + эксплуатант).

## 1. Принципы

1. **Факт неизменяем.** Записи только добавляются; исправление — новый факт со ссылкой на старый.
2. **Ограничение — предикат над фактами.** Проверка не вызывает другую проверку и не решает «как искать».
3. **Вердикт — не факт-мнение, а производное от фактов.** Мнение модели хранится отдельно (`judgment`) с провенансом.
4. **Представление (view) не хранится как истина.** Панель, статусы, свежесть — вычисляются.
5. **Недопустимое состояние непредставимо.** Схема + ограничения не дают построить запись без доказательств.
6. **Проверка проверяющего не нужна.** Вместо неё — свойство «ограничение краснеет», проверяемое генерацией фактов.

## 2. Отношения (append-only, в хеш-цепочке)

| Отношение | Поля | Смысл |
| --- | --- | --- |
| `task` | id, contract_hash, base_commit, risk, declared_paths, at | задача как тип: контракт и границы |
| `contract` | task, hash, criteria, allowed_paths, no_touch, at | сам контракт (immutable blob + hash) |
| `diff` | task, base, commit, paths, diff_hash, at | что фактически изменено |
| `evidence` | task, kind, artifact_hash, exit, seal_hash, at | доказательства: test_run, sealed_run, gate_run, journal_link |
| `judgment` | task, artifact_hash, by, model, verdict, rationale_hash, independent, at | суждение о конкретном артефакте (хеш обязателен) |
| `accept` | task, contract_hash, diff_hash, evidence_set_hash, by, at | **свидетельство**: задача принята именно с этим диффом и этим набором доказательств |
| `release` | version, tag, asset, size, smoke_hash, receipt_hash, at | выпуск |
| `ruleset` | version, anchors_hash, presets_hash, policy_json, at | правила как данные (миграция — новая запись) |

Производные (view, не хранятся): `status(task)`, `panel`, `stale(ruleset)`, `open_obligations`, `residual_risk`.

## 3. Ограничения

```
C1  accept(t) ⇐ diff(t, commit, paths) ∧ contract(t, hash=task.contract_hash)
C2  accept(t) ⇐ evidence(t, kind=sealed_run, seal_hash=ruleset.seal, exit=0)
C3  ∀p∈diff.paths: p ∉ forbidden(tests/, sealed/, presets/)
C4  accept(t) ⇐ judgment(t, artifact_hash=diff.diff_hash, independent=1, verdict=accepted)
C5  accept(t) ⇐ ∀g∈policy(ruleset, task.risk): evidence(t, kind=gate_run, gate=g, exit=0)
C6  release(v) ⇐ asset(v) ∧ smoke_hash(v) ∧ receipt_hash(v) ∧ tag = v
C7  ∀ факт: prev_hash = hash(предыдущий) — разрывов нет
C8  findings(t) ⊇ {(cmd,path): факт ∉ planned(t)} — план против фактических действий
C9  ruleset(v+1) ⇐ подпись human-ключа над hash(ruleset(v))
C10 accept(t) атомарен: свидетельство и метаданные в одном коммите
```

Читается как SQL: `accept` возможен только там, где подзапросы дают непустой результат.
Проверка = запрос, вернувший пусто ⇒ нарушений нет.

## 4. Что происходит с 59 проверками

| Группа | Судьба |
| --- | --- |
| `acceptance-p0`, `acceptance-record`, `acceptance-schema`, `acceptance-schema-fields` | одна схема + C1/C10 |
| `ci-behavior`, `ci-config`, `ci-guard-step` | одно ограничение «CI ведёт себя по контракту» |
| `release-hygiene`, `release-receipt`, `release-update` | C6 (+ существующий релизный гейт) |
| `contract-*` (3) | схема контракта (тип), C1 |
| `engine-*` (3), `panel-*` (3), `doctor-*` (2), `deployed-copy` | миграция/развёртывание, не гейт задачи |
| `narrow-*`, `pipe-free`, `fetch-retry` | одно ограничение «среда» |
| `covers-severity`, `criteria-overlap`, `parallel-criteria`, `targeted-tests` | ограничения над `contract.criteria` (C1-производные) |
| `report-honesty`, `judge-discipline`, `actor-sources`, `launch-evidence` | C4 + провенанс `judgment` |
| `journal-integrity`, `gates-journal`, `gate-rules`, `gate-output`, `gate-diagnostics` | C7 + один view |
| `foreign-workspace`, `workspace-imperative`, `node-attribution` | остаются: это про доступ, а не про приёмку |
| `anchor-freshness`, `node-presets` | C9: правила как данные, подпись человека |
| `loop-detector`, `wait-guard`, `job-runner` | остаются: наблюдение за процессом |

Цель: **15–18 ограничений и один исполнитель** вместо 59 модулей; каждая оставшаяся проверка обязана иметь
негативный кейс (известный плохой набор фактов, на котором она краснеет).

## 5. Свойство «проверка краснеет»

Для каждого ограничения: минимальный набор фактов, удовлетворяющий ему; затем по одному удалению каждого
обязательного факта — ограничение обязано отказать. Плюс мутации: ослабленный тест, удалённый тест,
поддельная квитанция, подменённый журнал, чужой `artifact_hash` в суждении.

Это заменяет «проверяющего проверяющих»: свойство генерируемо и не требует третьего мнения.

## 6. Миграция

| Этап | Что | Критерий перехода |
| --- | --- | --- |
| P0 | файл схемы + исполнитель читает существующие артефакты, ничего не меняя | вердикты совпадают с текущими на 3 задачах |
| P1 | C1–C5 в **теневом режиме** (только отчёт) | 5 задач без расхождений или расхождения объяснены |
| P2 | `task-accept` переключается на исполнителя; старые проверки — за шимом | приёмка проходит, негативные кейсы краснеют |
| P3 | удаление дублей | набор тестов зелёный, selftest без потери шагов |

## 7. Риски и честные границы

1. **Выразительность.** Семантическое суждение не сводится к фактам; оно живёт как `judgment` с хешем артефакта —
   проверяется полнота и провенанс, а не «правильность мнения».
2. **Производительность.** Запросы по журналам — это индексы: факты выносятся в компактные файлы на задачу.
3. **Обратная совместимость.** Записи v1 читаются конвертером; конвертация пишет новые факты, старые не меняет.
4. **Соблазн «ограничения над ограничениями».** Запрещено правилом: третьего уровня в потоке нет, только выборочный аудит.
5. **Человеческая подпись.** C9 сохраняет её обязательность: правила меняются миграцией с подписью, а не правкой модуля.
