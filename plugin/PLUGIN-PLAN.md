# План: плагин управления workflow (read-only, v1)

Решения заказчика 2026-10-26:

1. **Первая версия — только чтение.** Никаких кнопок, пишущих артефакты.
2. **Правка `policy` из UI не делается** — только показ и ссылка на файл.
3. **Монорепозиторий**: плагин живёт в `subagent-workflow/plugin/`.
4. **Ни `/wf`, ни инструментов для модели в v1** — только панель.

## Принцип

UI — вид над репозиторием, а не второе состояние. Все данные читаются из
артефактов задачи и `workflow.config.json`; гейты не запускаются (в v1) и не
переписываются. Один и тот же вычислитель состояния позже используют и
read-only панель, и будущие действия, чтобы UI и CI не разошлись.

## Что показывает v1

### Доска

Список задач из `config.tasksDir` со стадией, вычисленной по файлам:

| Стадия | Условие |
| --- | --- |
| `контракт` | есть `task.md` и `criteria.json`, нет `criteria.lock` |
| `атака` | `policy.attack != off` и нет `attack.json` (или есть нерешённый `blocking`) |
| `замок` | есть `criteria.lock`, нет `red.json` |
| `красный` | есть `red.json`, `redProven: true`, нет `verify.json` |
| `зелёный` | `verify.json.allPassed: true`, нет `acceptance.json` |
| `принято` | есть `acceptance.json`, версия 4/5/6 |
| `замечания` | запись с `releaseReady: false` (assumed-решения / review) |

Риск, заголовок, дата, ссылки на артефакты — рядом. Если замок не совпадает с
контрактом — метка «рассинхрон» (через `task-hash --verify` в read-only режиме
не запускаем; сравнение — по `criteria.lock` и хешам файлов).

### Карточка задачи

- цель, риск, `issuedBy` (сессия/модель), `allowedPaths`/`protectedPaths`;
- решения: `class`, `impact`, доказательство, `assumed` — заметно;
- критерии: команда, ожидание, `covers`; карта покрытия, если `verify.json` есть
  (`coverage.uncovered` — красным);
- атака: находки, `blocking` без `resolution`, критик (сессия/модель/семейство);
- запись: версия, `actor.family`, `independence.modelLevel`, `releaseReady`,
  `review`, кандидатный и metadata-коммиты;
- `git log` по путям задачи (контракт, красный, кандидат, приёмка).

### Политика и роли

Эффективные значения `policy` (как их видит `doctor`), реестр `models`, роли.
Предупреждения: одинаковое семейство роли и постановщика; `assumed`; непокрытые
файлы; `blocking` без решения; `releaseReady: false`.

## Чего в v1 нет

- запуска гейтов, кнопок «verify/hash/accept», любых записей в репозиторий;
- правки `policy`, `roles`, `models` (только чтение и ссылка на файл);
- `/wf`-команды и инструментов модели;
- собственной базы/кэша: только файлы, кэш — на время отрисовки.

## Архитектура

```
plugin/
  package.json          name: dsh-workflow-console, dsh.bundle.patch, dsh.client
  cordis.patch.yml      insert: id dsh-workflow-console
  lib/index.js          apply(ctx, config): web + settings (+ client bundle)
  lib/state.js          репозиторий → состояние (чистые функции, тестируемые)
  lib/api.js            GET /workflow/api/status|tasks|task/:id|policy
  lib/client.js         панель: доска, карточка, политика
  test/state.test.mjs   фикстура: скопированный examples/minimal
```

- Корни репозиториев: `cwd` сессии по умолчанию + список в настройках плагина.
- Маршруты — loopback-only, как у `dsh-llm-memory`; ключи не читаются.
- Состояние строится только чтением: `task.md` (TASK-META), `criteria.json`,
  `criteria.lock`, `attack.json`, `red.json`, `verify.json`, `acceptance.json`,
  `workflow.config.json`, `git`.
- UI: слот `conversation.view` (вкладка «Workflow»), стиль — как у остальных
  панелей DSH; без собственных зависимостей сверх react.

## API (только GET)

| Маршрут | Ответ |
| --- | --- |
| `GET /workflow/api/status` | корни, выбранный репозиторий, версия пакета из SPEC, политика |
| `GET /workflow/api/tasks` | список задач со стадией и флагами |
| `GET /workflow/api/task/:id` | карточка целиком |
| `GET /workflow/api/policy` | политика, модели, роли, предупреждения |

## Критерии приёмки v1

1. Панель открывается в DSH и показывает задачи реального репозитория.
2. Стадии совпадают с тем, что видно по файлам вручную (тест на фикстуре).
3. Карточка показывает `assumed`-решения, находки атаки и `releaseReady`.
4. Политика и роли — те же, что печатает `doctor`.
5. Ни один файл репозитория не меняется после работы панели (проверить `git status`).
6. Тест `state.js` на фикстуре; сборка клиента проходит.

## Решённые вопросы (2026-10-26, новая сессия)

1. **Клиентский бандл.** DSH 0.2.1-rc.3 принимает `dsh.client.platform: "web"` +
   `exports["./client"]`; хост сам отдаёт `lib/client.js`, сборщик не нужен.
   Слоты — `ctx.slots.inject("conversation.view", …)`, как у `dsh-llm-memory`.
2. **Версия пакета.** Читается из `docs/subagent-workflow/VERSION` (в развёрнутом
   каталоге его нет), fallback — строка `Версия:` в `SPEC.md`. В API показаны
   обе: `packageVersion` и `specVersion`.
3. **Корни и текущий workspace.** `roots` — список абсолютных путей в
   `cordis.patch.yml` профиля. Клиент читает текущий workspace из сервиса DSH
   `uiWorkspace` и открывает его, если там есть workflow; иначе откатывается на
   первый настроенный корень и пишет это в строке расположения. Host разрешает
   `?root=` для настроенных корней и зарегистрированных workspace.

## Решения по упаковке и CI (2026-10-26)

1. **Плагин — отдельный пакет.** `plugin/` не входит в релизный архив:
   `tools/pack.mjs` исключает каталог. `init` копирует только `spec/`, поэтому
   в развёрнутое пространство плагин и так не попадает. Установка — link-зависимость
   профиля, см. `plugin/README.md`.
2. **Сборки клиента нет.** Клиент — classic JS на `React.createElement`; хост
   отдаёт готовый `lib/client.js`. В CI добавлена джоба `plugin`:
   `node --test plugin/test/` и `node --check plugin/lib/client.js`.
3. **Границы v1 соблюдены:** только GET, ни одного POST/PUT; policy только
   отображается; ни `/wf`, ни инструментов модели; собственного кэша нет.

## Состояние реализации

- `plugin/lib/state.js` — чистые функции и единственный адаптер чтения; стадии,
  флаги, решения, покрытие, атака, записи v3–v6.
- `plugin/lib/api.js` — `/workflow/api/status|tasks|task/:id|policy|compat`,
  loopback-only.
- `plugin/lib/compat.js` — чистые правила стыковки версий: VERSION/SPEC,
  обязательные скрипты, версии замков и записей, ограничение функций и
  рекомендации (только текст, ничего не запускается).
- `plugin/lib/client.js` — слот `conversation.view`: доска → карточка →
  политика → совместимость; строка «текущий workspace / показан»; пустые
  колонки скрыты, стадии объяснены.
- Тесты: 25 state + 11 API + 5 client + 9 compat; dev-server проверен `curl`.
- Проверка на `ws-school-app` (только чтение): 30 задач, 18 принято, 12 контракт;
  policy совпала с doctor. В реальном репозитории нашлись записи v3 и
  `acceptance.json` в UTF-16LE — плагин читает и то, и другое.

## Порядок работы

1. Каркас пакета + `state.js` + тест на `examples/minimal`.
2. HTTP-маршруты + проверка через curl.
3. Клиентская панель: доска → карточка → политика.
4. Установка в профиль, проверка на `ws-schooll-kids-design` или новом репозитории.
5. Только после этого — обсуждение v2 (действия, роли, запуск моделей).
