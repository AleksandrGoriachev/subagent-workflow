# Спецификация: делегирование субагентам с проверяемой приёмкой

Версия: 2.6.0. Дата: 2026-10-28.
Статус: проект-независимая, готова к разворачиванию в новом репозитории.
Основание: редакция 1.3 (роли, риск-уровни, контракт, свежий прогон, redExpect) плюс
исправление главного дефекта — роль приёмщика проверяется машиной, а не декларацией.

Документ не привязан к предметной области, языку, git-хостингу и харнессу агентов.
Везде, где есть оркестратор и отдельный исполнитель, действуют одни и те же правила.
Конкретные имена переменных и инструментов вынесены в «адаптеры» (раздел 13).

## 0. Что нового в редакции 2.0

1. **Аттестация актора.** Приёмщик предъявляет идентификатор своей сессии; постановщик
   записан в контрактном коммите; совпадение — отказ. Запись содержит `actor`.
2. **Асимметричная подпись.** Ed25519 вместо HMAC: публичный ключ — в репозитории,
   приватный — вне доступа исполнителя. Проверять может кто угодно.
3. **Уровень независимости** — обязательное поле записи, а не пожелание: `declared` /
   `separate-session` / `human`, с минимумами по риску.
4. **Проверка записей в CI.** Не только запись создаётся — она проверяется на каждом PR.
5. **Честные границы.** Спецификация не обещает невозможного: подпись — это
   tamper-evidence; настоящая независимость требует разделения окружений (раздел 11).

Что документ **не** заменяет: код-ревью, security review, продуктовую приёмку и
решение заказчика. Автоматические проверки доказывают поведение, но не ценность.

Версия 2.0.1 подтягивает правило 1.4.1: замечания приёмщика разбираются и
классифицируются, «принято с замечаниями» не равно «готово к выкатке».

Версия 2.0.2 закрывает два дефекта, найденных при развёртывании:

1. **Скан секретов не читает чужие строки.** Полный текст файла сканируется только
   для неотслеживаемых файлов; изменённые дают лишь строки диффа. Иначе любая задача,
   трогавшая файл с давним `apiKey: env.…`, падала на предсуществующей строке (1.4.2).
2. **`init` не копирует `acceptors.json`.** Это состояние рабочего пространства, а
   не шаблон: скопированный файл заставляет `init` пропустить генерацию ключа, и новый
   репозиторий остаётся с публичным ключом без приватного.

Версия 2.0.3 не меняет правил процесса: развёртывание проверяется отдельным
сценарием (`e2e-deploy.mjs`) и отдельной джобой CI, чтобы эта регрессия была видна
сразу, а не внутри полного прогона. Пакет распространяется по лицензии MIT.

Версия 2.1.0 закрывает слепую зону «код ↔ критерии ↔ замысел»:

1. **Решения задания.** Семантический выбор («что считается доставкой») записывается в
   контракт явно и не может остаться неподтверждённым незамеченным: либо исполняемый
   критерий, либо подтверждение человека; иначе `assumed` и `releaseReady=false`.
2. **Покрытие.** Критерий объявляет `covers`; `verify` валит изменённый файл, для
   которого нет ни одной проверки. Раньше зелёный прогон молчал о таком файле.
3. **Запись версии 5** хранит digest решений; `check` пересчитывает его по контракту
   кандидата, поэтому спрятать `assumed` нельзя.

Версия 2.2.0 добавляет атаку спецификации и настраиваемую строгость:

1. **Критик до реализации.** Отдельная роль и шаг `task-attack`: находки классов
   `missing-case`, `ambiguous-criterion`, `contradicts-invariant`,
   `undefined-failure-mode`, `unverifiable-claim`, `scope-creep`; `blocking` без
   решения не даёт запереть контракт.
2. **Политика вместо догмы.** `policy` в конфигурации: по каждому правилу `fail`,
   `warn` или `off`. По умолчанию атака выключена, поэтому обновление не ломает
   текущие задания; строгость включает репозиторий.
3. **Роли и модели.** `roles` и реестр `models`; запись фиксирует семейство
   приёмщика и критика, но проверка семейства — по политике: это декларация, а не
   доказательство.

Версия 2.2.1 — правка документации развёртывания: `deploy/AGENT-DEPLOY.md`
приведён к редакции 2.2 (шаг атаки, `decisions`, `covers`, политика, миграция
замка и записи). По ней агент разворачивает пакет, поэтому отставшая инструкция
была дефектом поставки, а не документации.

Версия 2.2.2 — упаковка и четыре правила, найденные ночным разбором 2026-10-26:

1. **`VERSION` доезжает до рабочего пространства.** `init` кладёт номер версии в
   развёрнутую копию (`docs/subagent-workflow/VERSION`), и читать его можно там же,
   где лежат ворота, а не догадываться по строке в `SPEC.md`.
2. **Панель DSH — отдельный пакет.** `plugin/` (`dsh-workflow-console`) не входит
   в релизный архив: это хост-пакет, а не часть переносимой спецификации.
   Установка — `plugin/README.md`.
3. **I-29. Диагноз — по состоянию, а не по тишине.** Объяснять отказ можно только
   после чтения фактического состояния; журнал обязан писать оба перехода.
4. **I-30. Повтор симптома — повод проверить, а не повторить.** «Попробуй ещё»
   недопустимо, пока не установлено, доходят ли запросы до системы.
5. **I-31. Критерий — наблюдаемый эффект.** «Команда вернула 0» не доказывает, что
   пользователь получил результат.
6. **I-32. Перевыпуск — новое задание.** Приёмка и красный прогон не наследуются.
7. **I-33. Регресс и долг провенанса — разные вещи.** Падение критерия закрытого
   задания — регресс, он валит прогон всегда. Отсутствие красного у low с записанным
   обходом — законный долг: предупреждение и baseline. Medium/high без красного или
   low без записанного обхода — нарушение.

Версия 2.3.0 делает эти правила машинными:

1. **Эффект критерия.** Поле `effect { observable, threshold, measuredBy }`;
   если решение влияет на пользователя, критерий с эффектом обязателен
   (`task-lint`, `task-accept`; строгость — `policy.decisions`).
2. **Свежесть красного.** Для записей версии 6 `red.baseSha` обязан совпадать с
   `contractCommit`: перевыпуск не наследует старый красный прогон.
3. **Гейт `task-regress`.** Принятые задания перезапускаются на текущем HEAD:
   `ok`, `regressed`, `unproven-lawful`, `unproven-violation`, `untrusted`,
   `legacy`, `error`; в CI — по расписанию, долг — через `regress.baseline.json`.

Версия 2.3.1:

1. **Обновление не ломает доказательства.** `init --force` обновляет файлы пакета и
   больше не перегенерирует ключ; ротация — только `--rotate-key`. `VERSION` пишется
   тогда и только тогда, когда файлы действительно обновлены.
2. **Эффект измеряется другим критерием.** `effect.measuredBy` обязателен и не может
   указывать на сам критерий; `verify` записывает эффект, запись хранит `effects`.
3. **Долг провенанса отделён от регресса.** Записи 1–3 — `legacy` (не ошибка);
   `unproven-lawful` (low + записанный обход) — предупреждение; `unproven-violation` —
   ошибка; baseline фиксирует известный долг с `reviewBy` (30 дней).

Версия 2.3.2:

1. **Baseline не скрывает регресс.** `regressed`/`error`/`untrusted`/
   `unproven-violation` валят прогон всегда; baseline гасит только `unproven-lawful`.
   `--write-baseline` пишет только законный долг, нарушения — `--include-violations`.
2. **`check` проверяет эффект.** `accept` пишет `effectsRequired` и `effects`;
   записи до 2.3.2 флага не имеют и не ломаются.
3. **`init --force` сохраняет политику.** `workflow.config.json` проекта не
   перезаписывается файлами пакета.

Версия 2.4.0:

1. **I-34. Доказательство решения и эффект — одна цепь.** Решение с влиянием на
   пользователя, опирающееся на исполняемый критерий, обязано ссылаться на носитель
   эффекта или его измеритель: `evidence.ref ∈ {effect.criterion, effect.measuredBy}`.
2. **Связь проверяется машиной.** `lint`/`verify`/`accept` не пропускают разрыв
   цепи; `verify.json.effects.links` и `effectConsistency` записи хранят связь;
   `check` пересчитывает её по контракту кандидата. Записи до 2.4.0 не ломаются.
3. **`check` применяет политику и к эффекту.** `effects` и `effectConsistency`
   подчиняются `policy.decisions` (раньше пустой `effects` валил CI безусловно).

Версия 2.4.4:

1. **Порядок коммитов описан.** В «Быстром старте» появился раздел «Порядок

3. **Чек-лист выкатки дополнен прогоном одной задачи целиком** на развёрнутой

Версия 2.4.5:

1. **`init` ставит свежий mtime развёрнутым файлам.** На Windows копирование
   сохраняет время источника, а архив собран с постоянными метками. Обновление,
   которое не меняет размер файла (VERSION 2.4.3 → 2.4.4, строка `TOOL`), после
   такого копирования не видно git'у: stat-кеш считает файл неизменённым, и
   `git status` молчит. Обновление можно закоммитить «успешно», оставив старый
   `TOOL` — та же ошибка, что в 2.4.2, только другим путём. Теперь `init` выставляет
   время скопированных файлов на «сейчас», и правка видна.
2. **Это закреплено проверкой** в `e2e-deploy`: «развёрнутые файлы получают свежий
   mtime (git увидит обновление)».
3. **В «Порядке коммитов» добавлено правило 5:** после `init --force` `git status`
   обязан показать изменённые файлы пакета; пусто при новых версии и `TOOL` —
   повод обновить время файлов и повторить `git add -A`.

Версия 2.4.6:

1. **Движок не защищаем хешем задания.** `protectedPaths` не должен накрывать сам
   пакет (`docs/subagent-workflow/**`): обновление пакета через `init --force`
   меняет эти файлы, замок задания краснеет, а перезамок после красного запрещён
   (I-3) — задание навсегда остаётся в ошибке. Защищайте свои проверки
   (`checks/**`, `tests/**`) и артефакты задания: движок защищён версией пакета
   (поле `tool` в `criteria.lock`).
2. **`task-lint` говорит об этом словами** — предупреждение, а не молчание. Не
   ошибка: задание может осознанно заморозить движок на время работы, но тогда
   последствие названо.
3. **Случай, который это вскрыл:** задание 0001 в `default-workspace` защищало
   пакет; пакет обновили 2.4.3 → 2.4.5, пять файлов разошлись с хешами, и ни
   `check-acceptance`, ни `doctor`, ни условия выпуска этого не показывали —
   увидела панель (`lock-mismatch-protected`), подтвердил `task-lint`.

Версия 2.4.7:

Версия 2.4.9:

1. **Послабление по `contractCommit` узкое с двух сторон.** `verifyLock` принимает
   `options.acceptedTolerant` (по умолчанию `false`), и передаёт его один
   `task-lint`. Задание считается принятым только при валидной записи: файл есть,
   разбирается как JSON, `record.status === 'accepted'`. Пустой, битый файл или
   чужой статус основанием не является: в 2.4.8 наличие файла снимало ошибку и в
   `task-verify`, и в `task-accept`, обходя инвариант «HEAD не двигался после

2. **Формулировка о `task-accept` исправлена.** Он сравнивает `verify.headSha` с
   `lock.contractCommit` и текущий HEAD не читает; сдвиг HEAD после verify ловит
   `verifyLock`, сравнивая замок с фактическим HEAD.
3. **Проверки в `e2e`:** до приёмки без `acceptance.json` и с пустым, битым или

   файлом отказывает; G7 требует `WARN`, а не подстроку.

Версия 2.5.0:

1. **Коммит без задания отклоняется.** Гейт `scripts/task-guard.mjs` проверяет
   покрытие изменения: `--staged [--message <text>]` для индекса,
   `--range <from..to>` для диапазона, `--audit [--range]` — отчёт о метках
   обхода и нарушениях (всегда exit 0). Настройки — блок `guard` в
   `workflow.config.json`; при `enabled !== true` скрипт молчит и выходит 0.
2. **Покрытие (D3).** Активное задание — с `criteria.lock` и без
   `acceptance.json`; его `allowedPaths` покрывают пути. Каталог
   незакрытого задания `docs/tasks/<id>/**` покрывает себя сам — иначе
   контракт нового задания не закоммитить (замка у него ещё нет). Плюс
   `guard.allow` и метка обхода в сообщении коммита.
3. **Хуки ставятся локально.** `init` копирует `hooks/` с правом исполнения и
   выставляет `git config core.hooksPath docs/subagent-workflow/hooks`; повторный
   `init` идемпотентен, глобальный конфиг не меняется. Решение принимает
   `commit-msg`: git отдаёт сообщение коммита только ему, а метка обхода живёт в
   сообщении. `pre-commit` показывает непокрытые пути и не отказывает.
4. **Панель пишет только флаг.** `writeGuardEnabled` меняет `guard.enabled`
   (остальные ключи байт в байт) и дописывает строку в `guard.log` с ISO-временем
   и актором: оба перехода фиксируются (I-29). Полномочия панели этим исчерпаны.
5. **Пределы честные.** `--no-verify` пропускает хуки целиком; метка обхода не
   запрещается, а остаётся в аудите.

   отдельный кейс), существующие шаги CI не удаляются и не ослабляются.
2. **Поведение пакета не меняется.** Версия 2.5.1 в пяти местах и секция
   CHANGELOG; правок кода ворот нет.

Версия 2.5.2:

1. **Право исполнения хуков — часть поставки.** `spec/hooks/pre-commit`,
   `commit-msg` и `pre-push` лежат в git с режимом `100755`: checkout на Linux
   получает право исполнения из индекса, а не из настройки раннера. Windows
   режим не хранит — он выставляется только git-ом (`git update-index
   --chmod=+x`), и это единственный способ закрепить его в поставке.
2. **Кандидат переносит режим из индекса.** Сборка кандидата
   (`spec/scripts/task-accept.mjs`, `createCandidate`) после `git add`
   возвращает `100755` тем путям, что помечены исполняемыми в реальном
   индексе: режим читается `git ls-files -s`, переносится
   `git update-index --chmod=+x` в индекс кандидата. `git add` берёт режим из
   рабочего дерева и на Windows его теряет, поэтому принятое дерево расходилось
   с проверенным. Содержимое не меняется — только режим; путь без метки в
   индексе остаётся `100644`.
3. **CI не подменяет права.** Шаг `chmod +x spec/hooks/*` удалён; сразу после
   `e2e` в джобе `test` идёт `node spec/checks/hooks-mode.mjs` — проверка
   режима в индексе и отсутствия подмены прав. Проверка, зелёная в CI и красная
   локально, хуже отсутствующей: она создаёт видимость покрытия.

Версия 2.6.0:

1. **DSH — один из источников, а не обязательный.** Источник актора —
   настраиваемая цепочка `actor.sources` (`{ env, kind }`); первый непустой

3. **Основание видно в записи.** Запись v6 получает `actor.source`,

4. **Проверки и шаблон.** `spec/checks/actor-sources.mjs` — 8 сценариев

5. **Схема записи знает поля 2.6.0.** `spec/templates/acceptance.schema.json`:

## 0.1. Быстрый старт с нуля

Пакет самодостаточен: в нём есть все ворота, шаблоны, конфигурация и загрузчик
рабочего пространства. Ничего «дописать по месту» не требуется.

~~~bash
# 1. развернуть рабочее пространство в репозитории
node scripts/init.mjs --repo <проект> --key-id agent-judge

# 2. создать задание (issuedBy берётся из окружения постановщика)
node scripts/new-task.mjs --repo . --id 0001 --title "..." --risk medium

# 3. заполнить критерии и закоммитить контракт — ЭТОТ коммит станет контрактным
git add docs/tasks/0001 checks && git commit -m "task 0001: контракт"

# 4. ворота до работы: замок и красный — на том же HEAD, что и в шаге 3
node scripts/task-hash.mjs --task docs/tasks/0001 --write
node scripts/task-lint.mjs --task docs/tasks/0001 --strict
node scripts/task-red.mjs  --task docs/tasks/0001 --base HEAD
# criteria.lock, red.json и red.log остаются незакоммиченными: коммит сдвинет
# HEAD и сломает инвариант замка (см. «Порядок коммитов» ниже)

# 5. работа исполнителя в отдельной сессии; кандидат НЕ коммитится
node scripts/task-verify.mjs --task docs/tasks/0001

# 6. приёмка из ДРУГОЙ сессии, ключом приёмщика; ворота сами создают
# кандидатный коммит-объект и пишут его SHA в запись
node scripts/task-accept.mjs --task docs/tasks/0001 --acceptor judge \
  --key ~/.wf-keys/agent-judge.key.pem --key-id agent-judge

# 7. проверка записи и фиксация: ветка встаёт на кандидата, запись — отдельным коммитом
node scripts/task-check-acceptance.mjs --file docs/tasks/0001/acceptance.json --repo . --metadata HEAD
git reset --hard <candidateCommit>
git add docs/tasks/0001/acceptance.json && git commit -m "task 0001: приёмка (metadata)"
~~~

### Порядок коммитов: что двигает HEAD и когда

Ворота замораживают не только содержимое контракта, но и **коммит**, на котором
контракт заперт: `criteria.lock.contractCommit` — это `HEAD` в момент
`task-hash --write`, и `checkContractCommitted` ждёт, что `HEAD` этот не сдвинулся.
Практические следствия (проверены на живом проекте 2026-10-27):

1. **Замок ставится на контрактный коммит** (шаг 4 сразу после шага 3).
2. **`criteria.lock`, `red.json`, `red.log` до `task-verify` не коммитятся.**
   Коммит artefact-файлов сдвигает `HEAD`, и `task-verify` отказывает:
   `lock: contractCommit: ожидалось <контракт>, сейчас <новый HEAD>`. Артефакты
   запираются/подписываются не ради истории, а ради свежести дерева.
3. **Кандидат не коммитится руками.** `task-accept` сам создаёт коммит-объект с
   принятым деревом (ветка не двигается) и пишет его SHA в запись.
4. **После `init --force` проверьте, что git видит обновление.** `init` выставляет
   скопированным файлам свежий mtime (2.4.5), но если `git status` пуст при новых
   `VERSION` и `TOOL` — время не обновилось: обновите mtime файлов и повторите
   `git add -A`. Иначе правка того же размера молча останется в индексе старой.
5. **Фиксация — два шага после приёмки:** `git reset --hard <candidateCommit>`
   (ветка встаёт на принятое дерево) и отдельный коммит с `acceptance.json`.
   Отдельный — потому что metadata-коммит проверяется отдельно: код в нём
   меняться не должен.

Самопроверка пакета: `node selftest.mjs` (правила записи), `node e2e.mjs`
(полный цикл на временном репозитории, включая отказ самоприёмке) и
`node e2e-deploy.mjs` (развёртывание из уже развёрнутого каталога).

## 1. Термины

| Термин | Значение |
| --- | --- |
| Задание | Отдельный файл с целью, границами, инвариантами, средой, критериями и `issuedBy` |
| Контракт | `task.md`, `criteria.json` и защищённые проверки, закоммиченные до работы |
| Критерий | Одна команда (или check-скрипт) и наблюдаемое ожидание |
| Красный до | Прогон на базовом коде, где объявленные критерии падают по объявленной причине |
| Постановщик (issuer) | Тот, кто пишет задание и критерии; его сессия записывается в контракт |
| Исполнитель | Агент, который меняет код в разрешённых границах; не коммитит и не принимает |
| Приёмщик (acceptor) | Тот, кто исполняет проверки и подписывает запись; не является постановщиком и исполнителем |
| Аттестация актора | Предъявление идентификатора сессии/ключа, происходящего из окружения, а не из аргументов |
| Уровень независимости | `declared` < `separate-session` < `human`; минимум зависит от риска |
| Кандидатный коммит | Коммит-объект с принятым деревом; ветка не двигается |
| Запись о приёмке | `acceptance.json` версии 6: актор, решения, атака, подпись, сессии, хеши, кандидат |
| Атака спецификации | Находки критика до реализации: чего в задании нет и что сломается |
| Политика | `fail` / `warn` / `off` для правил `decisions`, `coverage`, `attack`, `roles` |
| Защищённые файлы | Тесты, check-скрипты, фикстуры, конфиги проверок, lock-файлы |
| Flaky | Проверка, нестабильно падающая без изменения кода |

## 2. Роли и модель независимости

| Роль | Делает | Не делает |
| --- | --- | --- |
| Заказчик | Ценность, приоритет, смысл | Не пишет код и критерии |
| Постановщик (оркестратор) | Задание, критерии, красный прогон, выдача | Не принимает свою же работу |
| Исполнитель | Код в границах, самопроверка, отчёт | Не коммитит, не деплоит, не правит проверки |
| Приёмщик | Слепой прогон, дифф, подпись записи | Не готовил это задание и не писал код |
| Релиз-инженер | Коммит принятого SHA, выкатка | Не меняет критерии |
| Security reviewer | Угрозы, права, данные, секреты | Не подменяет приёмку поведения |
| Критик спецификации | Атакует задание до реализации: пропущенные случаи, неоднозначные критерии, необъявленные отказы | Не пишет код, не принимает, не меняет критерии |
| Наблюдатель (ретро) | Разбирает прошедшие сутки, предлагает изменения процесса | Не принимает, не меняет правила и код |

**Модель.** Независимость — это три наблюдаемых факта, а не должность:

1. **Другая сессия.** Идентификатор приёмщика отличается от идентификатора
   постановщика (и от заявленного идентификатора исполнителя).
2. **Другой контекст.** Приёмщик не получает отчёт исполнителя до прогона проверок.
3. **Другой ключ.** Подпись сделана ключом приёмщика; для high-risk — ключом человека.

Уровни:

| Уровень | Что выполнено | Допустим для |
| --- | --- | --- |
| `same-session` | Сессия совпала с постановщиком | Никогда (запись недействительна) |
| `declared` | Актор назван, но окружение не подтвердило сессию | Только `low`, с записью обхода |
| `separate-session` | Сессия из окружения, отличная от постановщика | `medium` (минимум) |
| `human` | Ключ человека и `--human <кто>` | `high` (обязательно) |

**Императивы ролей.**

- **R-1. Постановщик не принимает.** Прогон приёмки из сессии постановщика — отказ
  ворот, а не замечание.
- **R-2. Исполнитель не принимает.** Если сессия исполнителя заявлена в отчёте, она
  не может совпасть с сессией приёмщика.
- **R-3. Приёмщик подписывает, релиз-инженер коммитит.** Подпись не даёт права писать
  в основную ветку.
- **R-4. High-risk — человек.** Агент готовит доказательства, человек подписывает
  своим ключом.
- **R-5. Критик — не постановщик.** Атака из сессии постановщика не считается:
  критик не должен подтверждать собственный замысел.
- **R-6. Наблюдатель не правит.** Ретро-разбор предлагает; изменение правил —
  отдельной задачей с критериями и приёмкой.

## 3. Императивы

**Задание и критерии**

- **I-1.** Задание — отдельный самодостаточный файл: цель, границы, инварианты, среда,
  критерии, `issuedBy`. Ссылка «см. переписку» запрещена.
- **I-2.** Нет работы без измеримого критерия: команда и ожидаемый результат.
- **I-3.** Контракт коммитится до красного прогона. Хеш критериев пишется в замок
  вместе с `contractCommit`. После красного прогона перезамок с другим содержимым
  запрещён — даже если замок удалён.
- **I-4.** Сначала красная проверка, падающая по объявленной причине. Пропуск — только
  `low` с явным `--allow-missing-red`, записанным в артефакты.
- **I-5.** Артефакт не заменяет поведение.
- **I-6.** Тесты и проверки не ослабляются; хеши проверяются по коммиту, а не по
  рабочей копии.
- **I-7.** Секреты не попадают в код, задание, логи и отчёт; ключи подписи — тем более.
- **I-8.** Объём не расширяется без согласования.

**Красный и зелёный прогон**

- **I-9.** `redExpect` объявляет `mustFail`, `mustPass` и причины. Для medium/high
  причины обязательны для каждого `mustFail`.
- **I-10.** Для medium/high обязателен негативный критерий (`tags: ["negative"]`).
- **I-11.** Зелёный прогон идёт только по закоммиченному контракту; `HEAD` равен
  `contractCommit`, иначе отказ.
- **I-12.** Границы, контракт и секреты проверяются **после** прогона критериев:
  файл, созданный setup/тестом/teardown вне allowlist, валит прогон.
- **I-13.** В кандидатный коммит попадают только проверенные пути.

**Приёмка**

- **I-14.** Приёмка — свежий прогон. Для medium/high `task-accept` сам запускает
  `task-verify` с одноразовым nonce; `verify.json` исполнителя — самопроверка.
- **I-15.** Актор аттестуется окружением. Для medium/high отсутствие сессии —
  отказ; заявленная вручную сессия (`declared`) недопустима.
- **I-16.** Сессия приёмщика не равна сессии постановщика и заявленной сессии
  исполнителя. Проверяется в `task-accept` и повторно в `task-check-acceptance`.
- **I-17.** Запись подписана Ed25519-ключом приёмщика; публичный ключ закреплён в
  репозитории. HMAC для новых записей запрещён.
- **I-18.** High-risk: ключ человека (`human-*`), `--human <кто>`, `securityReview: true`,
  `humanSignoff: true`. Обходы запрещены.
- **I-19.** Запись неизменяема. Исправление — новая запись с `supersedes`; старая
  остаётся в истории.
- **I-20.** Принятое дерево замораживается: кандидатный коммит фиксирует код;
  `acceptance.json` — отдельный metadata-коммит, который не меняет дерево кода.
- **I-21.** Запись проверяется машиной: CI прогоняет `task-check-acceptance` по каждому
  изменённому `acceptance.json` и блокирует нарушение.
- **I-22.** Доказательства дословные: команда, вывод, код возврата, SHA, nonce.
- **I-23.** Логи — доказательство только если они в репозитории. Хеш в записи
  допускается лишь для файла, входящего в кандидатный коммит.

**Коммит, релиз, откат**

- **I-24.** Финальный коммит кода не меняет дерево кандидата; хук/форматтер — повторный
  прогон.
- **I-25.** Сообщение коммита ссылается на ID задачи, хеши критериев, кандидатный SHA
  и nonce приёмщика.
- **I-26.** Деплой — по runbook, с проверкой целевой среды; откат проверен заранее.
- **I-27.** Миграции и удаление данных — всегда high-risk.
- **I-28.** Локальный зелёный — не продакшен.

**Диагноз, эффект, перевыпуск (2.2.2)**

- **I-29. Диагноз — по состоянию, а не по тишине.** Объяснять отказ и просить
  повторить можно только после чтения фактического состояния. Источник состояния
  обязан фиксировать оба перехода (включение и выключение); отсутствие записи в
  журнале не означает «выключено».
- **I-30. Повтор симптома — повод проверить, а не повторить.** При второй жалобе на
  тот же симптом новая гипотеза и «попробуй ещё» недопустимы, пока не установлено,
  доходят ли запросы до системы. В ответе указывается признак, который подтвердит
  успех.
- **I-31. Критерий — наблюдаемый эффект.** Критерий готовности описывает состояние
  или порог у пользователя, а не факт выполнения действия. Для доставки,
  уведомлений и интерфейса — целевой порог и замер, а не «команда вернула 0».
- **I-33. Регресс и долг провенанса — разные вещи.** Падение критерия закрытого
  задания — регресс, он валит прогон всегда. Отсутствие красного у low с записанным
  обходом — законный долг (предупреждение, baseline); medium/high без красного —
  нарушение. Нельзя смешивать «код сломался» и «при приёмке не было красного» в
  одном «fail»: в проекте с законными low-обходами такой сигнал перестают читать.
- **I-32. Перевыпуск — новое задание.** Новый каталог/ID означает новый контракт,
  новый красный прогон и новую запись; доказательства приёмки не наследуются.
  Падение критерия закрытого задания — регресс, а не шум.
- **I-34. Доказательство решения и эффект — одна цепь.** Если решение влияет на
  пользователя и опирается на исполняемый критерий, этот критерий обязан быть
  носителем объявленного эффекта или его измерителем:
  `evidence.ref ∈ {effect.criterion, effect.measuredBy}`. Иначе решение «доказано»
  одним критерием, а эффект объявлен на другом; связь между ними не проверяется.
- **I-35. Изменение вне задания не входит в историю.** Коммит и push
  проверяются `task-guard`: путь покрыт, если он входит в `allowedPaths`
  активного задания (есть замок, нет записи приёмки), лежит в каталоге
  незакрытого задания, входит в `guard.allow` или помечен в сообщении меткой
  обхода. Метка — запись для аудита, а не разрешение: `--audit` её печатает.
  `--no-verify` обходит хуки целиком, поэтому проверка локальная и не заменяет
  серверную (pre-receive).

С 2.3.0 поле `effect` и свежесть красного прогона проверяются машиной
(`task-lint`, `task-accept`, `task-check-acceptance`).

## 4. Риск-уровни

| Уровень | Когда | Обязательно | Уровень независимости |
| --- | --- | --- | --- |
| `low` | Документация, комментарии, форматирование, чисто тестовые правки | `task.md`, критерии, контрактный коммит, замок, `verify`, запись | `declared` (с обходом) или выше |
| `medium` | Обычная фича/дефект | Полный цикл, красный по `redExpect`, негативный критерий, свежий прогон, `red.json` | `separate-session` минимум |
| `high` | Права, платежи, PII, публичный API, миграции, удаление данных, секреты | Всё из medium + security review + human signoff + ключ человека + репетиция миграции + canary + проверенный откат + два приёмщика | `human` |

Правила:

1. Уровень определяет постановщик и фиксирует в контракте; понижение — только заказчик.
2. Миграция и удаление данных — high-risk даже «на одну строку».
3. High-risk не принимает агент единолично.
4. `securityReview`/`humanSignoff` для high — ошибка lint при отсутствии, а не warning.

## 5. Контракт задания

### 5.1. `task.md`

Обязательные разделы: `Цель`, `Что не входит`, `Инварианты`, `Границы знания`,
`Среда`, `Критерии приёмки`, `Отчёт`, `Коммит`. Таблица критериев обрамляется
маркерами `<!-- CRITERIA:BEGIN -->` / `<!-- CRITERIA:END -->`.

Метаданные (JSON в `<!-- TASK-META … -->`):

| Поле | Обязательно | Смысл |
| --- | --- | --- |
| `id`, `version`, `title`, `risk` | да | Идентификация и глубина процесса |
| `issuedBy` | для medium/high | `{kind, session, model}` постановщика; фиксируется до работы |
| `executor`, `acceptor` | да | Роли; `acceptor` — ожидаемый, не доказательство |
| `allowedPaths`, `protectedPaths` | да | Границы и защищённые проверки |
| `decisions` | для medium/high | Реестр решений сверх механической работы (может быть пустым) |
| `securityReview`, `humanSignoff` | для high | Обязаны быть `true` |
| `hashExclude` | нет | Что не входит в digest дерева |

### 5.2. `criteria.json`

~~~json
{
  "task": "0042",
  "setup": [], "teardown": [],
  "redExpect": {
    "mustFail": ["C1"],
    "mustPass": ["C2"],
    "reasons": { "C1": "ожидаемая подстрока падения" }
  },
  "criteria": [
    { "id": "C1", "command": "…", "timeoutMs": 120000, "covers": ["src/delivery/**"],
      "expect": { "exitCode": 0, "stdoutContains": "…" }, "tags": ["fast", "behavior"] },
    { "id": "C2", "command": "…", "expect": { "exitCode": 1, "stderrContains": "…" },
      "tags": ["fast", "negative"] }
  ]
}
~~~

Правила: одна точка входа на критерий; наблюдаемое ожидание; все не-manual критерии
объявлены в `redExpect`; `mustFail` не пуст; причины для `mustFail` — обязательны для
medium/high; manual-критерии не считаются автоматическим доказательством.

**Эффект (I-31).** У задачи с пользовательским эффектом (`decisions[].impact =
user-visible | public-contract`) критерий обязан описывать наблюдаемое состояние или
порог («квитанция о получении», «≤ 5 s»), а не факт вызова. Технический критерий
«exit 0» сам по себе эффект не доказывает. Поле `effect {observable, threshold,
measuredBy}`: `measuredBy` обязателен и обязан указывать на **другой** исполняемый
критерий (2.3.1: сам критерий измерителем быть не может — иначе эффект и проверка
неразличимы). Наличие эффекта обязательно, когда решение влияет на пользователя;
`verify.json.effects` и запись `effects` хранят объявленный эффект для аудита.

С 2.4.0 (I-34) решение с `impact = user-visible | public-contract`, опирающееся на
исполняемый критерий, обязано ссылаться на носитель эффекта или его измеритель:
`evidence.ref ∈ {effect.criterion, effect.measuredBy}`. Иначе доказательство решения
и эффект — две несвязанные записи. Обязательность самого эффекта считается по
`impact`, независимо от `class` решения; согласованность (I-34) применяется только к
`semantic`/`contract` с criterion-доказательством. `verify.json.effects.links` и
`effectConsistency` записи хранят эту связь, `check` пересчитывает её по контракту
кандидата.

**`covers`** — какие файлы (шаблоны путей от корня репозитория) критерий покрывает.
Для medium/high нужен хотя бы один критерий с `covers`: `verify` сопоставляет
изменённые файлы с объявленными покрытиями и валит прогон на файле, у которого нет
проверки. Документация (`**/*.md`), артефакты задания и `hashExclude` исключены.

### 5.3. Замок

`criteria.lock` версии 3 (v2 — история): хеши `task.md`, таблицы критериев, `criteria.json`,
защищённых файлов и `contractCommit`. Канонизация: UTF-8, LF, без хвостовых пробелов
и пустых строк по краям. `--write` отказывает, если контракт не закоммичен или если
`red.json` уже существует и замок отсутствует/отличается (заморозка после красного).

**Обновление пакета в проекте, где задания уже заперты (2.4.6).** Замок помнит хеши
защищённых файлов и версию пакета (`tool`). Если `protectedPaths` задания накрывает
сам пакет, `init --force` меняет эти файлы, и замок краснеет — законно и необратимо:
перезамок после красного запрещён (I-3). Поэтому движок не защищаем. Если такое уже
случилось, перезамковывать нельзя: задание остаётся историей со своим замком
(`tool` назовёт версию, на которой оно запиралось), а новые задания выдаются на
обновлённом пакете.

### 5.4. Решения и их доказательства

Решение — запись в `TASK-META.decisions` о выборе, который сделан **сверх**
механической работы. Цель не в бюрократии, а в честности: у части решений нет и
не может быть исполняемой проверки, и именно они проваливаются незамеченными.

~~~json
{ "id": "D1", "class": "semantic", "question": "что считается доставкой",
  "chosen": "квитанция о получении", "options": ["отправка", "квитанция"],
  "impact": "user-visible", "reversible": false,
  "evidence": { "kind": "criterion", "ref": "C3" }, "status": "confirmed" }
~~~

| Поле | Смысл |
| --- | --- |
| `class` | `mechanical` (проверяется кодом), `semantic` (выбор смысла), `contract` (контракт интерфейса снаружи) |
| `impact` | `internal` (внутри), `user-visible` (пользователь увидит), `public-contract` (внешний контракт) |
| `evidence` | `criterion` (исполняемый критерий), `spec` (раздел спецификации), `customer`/`human` (ответ человека) |
| `confirmation` | `{kind: customer\|human, who, at}` — кто и когда подтвердил |
| `status` | `confirmed` или `assumed`; по умолчанию выводится из доказательства |

Правила машины:

1. Для medium/high `decisions` обязателен (пустой массив — «решений сверх механических
   нет», это допустимо).
2. Для `semantic`/`contract` нужны `options` (≥2), `impact` и `reversible`.
3. `impact = user-visible | public-contract` требует исполняемого критерия или
   подтверждения — иначе `task-lint` отказывает, а `task-accept` не подпишет.
3a. Если такое решение опирается на `evidence.kind = criterion`, критерий обязан
   входить в цепь эффекта (I-34): быть носителем или измерителем. `spec`/`customer`/
   `human` и manual-критерий — исключения: это человеческое доказательство, связывать
   нечего.
4. `assumed` (нет доказательства, влияние внутреннее) не мешает работать и быть
   принятым, но даёт `releaseReady = false` и запрещён для high-risk.
5. Решения входят в `task.md`, значит замораживаются замком вместе с критериями, а их
   digest попадает в запись и пересчитывается проверкой по контракту кандидата.

Реестр — для постановщика и приёмщика. Исполнителю уходит императивная формулировка
требования, без вариантов и рассуждений: он не должен подстраиваться под замысел.

### 5.5. Атака спецификации (2.2.0)

До реализации критик читает только задание и критерии — не код, не отчёт — и ищет
то, чего в них нет. Задача не «согласиться», а сломать: привести конкретный случай,
на котором задание неоднозначно или молчит.

~~~json
{
  "version": 1,
  "task": "0042",
  "critic": { "session": "…", "model": "glm-5.3-flash", "attestedBy": "env" },
  "findings": [
    { "id": "A1", "class": "missing-case", "severity": "blocking",
      "claim": "не сказано, что считать доставкой при повторной отправке",
      "case": "отправка дважды за одну секунду", "resolution": "добавлен критерий C4" },
    { "id": "A2", "class": "ambiguous-criterion", "severity": "non-blocking",
      "claim": "C2 проверяет только текст ошибки", "case": "иной код возврата",
      "reason": "вне объёма" }
  ]
}
~~~

| Класс | Что означает |
| --- | --- |
| `missing-case` | Случай, которого в задании нет, а реализация обязана его решить |
| `ambiguous-criterion` | Критерий допускает два прочтения |
| `contradicts-invariant` | Требование противоречит инварианту |
| `undefined-failure-mode` | Не сказано, что происходит при отказе |
| `unverifiable-claim` | Утверждение, которое нельзя проверить |
| `scope-creep` | В задание просочилось лишнее |

Правила: `blocking` закрывается только `resolution`; `non-blocking` требует
`reason`; `follow-up` — `followUpId`. Критик обязан быть не постановщиком
(проверяется по сессии), а «другое семейство моделей» — политика, не догма:
по умолчанию предупреждение, включается `policy.roles.modelFamily = fail`.

Атака — заявление, а не подпись: запись хранит её digest и `attestation: declared`,
а `check` сверяет файл в кандидате. Строгость шага — `policy.attack`: `off`
(по умолчанию), `warn` или `fail`. При `fail` `task-hash --write` не запирает
контракт без атаки и с нерешённой `blocking`-находкой.

## 6. Ворота

Порядок обязателен; каждый шаг — отдельная команда с кодом возврата 0/1.

| Шаг | Вход | Что делает | Артефакт |
| --- | --- | --- | --- |
| `attack` | задание | Атака спецификации до реализации: находки, `blocking` требует решения | `attack.json` |
| `hash` | контракт | Канонический хеш, замок (включая digest атаки) | `criteria.lock` |
| `lint` | задание | Структура, метаданные, `issuedBy`, `redExpect`, негатив, решения, `covers`, `effect`, секреты, замок | вывод |
| `red` | база | Прогон на базовом коде, сверка с `redExpect`, причины | `red.json`, `red.log` |
| `verify` | рабочее дерево | Полный прогон, границы до и после, покрытие `covers`, секреты, digest | `verify.json` |
| `accept` | verify | Свежий прогон с nonce, аттестация актора, решения, атака (digest, находки), подпись, кандидат | `acceptance.json` |
| `check` | запись | Подпись, инварианты, кандидат, хеши, свежесть красного | exit 0/1 |
| `regress` | принятые задания | Перезапуск критериев закрытых задач на текущем HEAD; статусы `ok`/`regressed`/`unproven-*`/`legacy`/`untrusted`/`error` | `--out <file>` |

**`accept` — обязательные проверки перед записью:**

1. `verifyLock` зелёный; контракт не менялся.
2. Актор: сессия из окружения, `!== issuedBy.session`, `!== executorSession`.
3. Уровень независимости соответствует риску.
4. Для medium/high — `TASK_ACCEPT_KEY`-эквивалент: приватный ключ доступен, публичный
   закреплён.
5. `--expect-contract <sha>` (если передан) совпадает с `contractCommit` — защита от
   переписанного контракта.
6. High-risk: `securityReview`, `humanSignoff`, `--human <кто>`, ключ `human-*`.
7. Обходы записываются; для high их нет.
8. Политика `policy`: `fail` превращает соответствующее замечание в отказ, `warn` —
   в предупреждение с записью факта, `off` — не проверяет. Целостность записи
   (пункты 1–7) политикой не отключается.

### 6.1. Граница истории: `task-guard` (2.5.0)

Ворота из таблицы выше проверяют задание, но не мешают изменению попасть в
историю мимо него. `scripts/task-guard.mjs` стоит на границе коммита:

| Режим | Что проверяет | Код возврата |
| --- | --- | --- |
| `--staged [--message <text>]` | индексированные пути | 0 — покрыто; 1 — «не покрыт: <путь>» |
| `--range <from..to>` | каждый коммит диапазона на его собственном дереве | 0/1 |
| `--audit [--range]` | метки обхода и нарушения для отчёта | всегда 0 |

**Покрытие оценивается на дереве того коммита, где лежит изменение**, а не на
текущем рабочем дереве: после приёмки `acceptance.json` закрывает задание, и
штатный коммит, сделанный при открытом задании, иначе отклонялся бы при пуше
(дефект P1, задание 0004). Режим `--range` читает и сообщения коммитов, поэтому
метка обхода действует и на push, где `--message` нет (дефект P2).

Покрытие (D3): путь покрыт, если он входит в `allowedPaths` задания, активного
в этом коммите (`criteria.lock` есть, `acceptance.json` нет); лежит в каталоге
задания `docs/tasks/<id>/**` — целиком, пока задание открыто, и только его
артефактами (`acceptance.json`, отчёты, `verify`/`red`, `criteria.lock`,
`attack.json`) после закрытия, иначе metadata-коммит приёмки блокировался бы
собственным хуком; входит в `guard.allow`; либо в сообщении коммита есть метка
обхода. Настройка:

~~~json
"guard": { "enabled": true, "mode": "fail", "allow": ["docs/**"],
           "bypassMarker": "workflow-bypass" }
~~~

При `enabled !== true` скрипт молча выходит 0: выключенный guard не меняет
поведение репозитория. `mode`: `fail` — отказ, `warn` — печать и exit 0,
`off` — не проверять.

`init` ставит `core.hooksPath` **локально** на `docs/subagent-workflow/hooks`,
копируя `pre-commit`, `commit-msg` и `pre-push` с правом исполнения. Решение
принимает `commit-msg`: git отдаёт сообщение коммита только ему, а метка обхода
живёт в сообщении. `pre-commit` печатает непокрытые пути и не отказывает;
`pre-push` проверяет диапазон `remote..local`, а для новой ветки — коммиты,
которых нет ни в одном remote.

Пределы названы честно: `git commit --no-verify` и `git push --no-verify`
пропускают хуки целиком — в аудите этого следа не остаётся. Метка обхода не
запрещается: `--audit` её печатает. Проверка локальная: это не pre-receive и не
защита от владельца машины. Панель переключает только `guard.enabled` и
дописывает строку в `guard.log` (I-29).

   для версий 5 и 6 обязателен `decisions`. Записи 1–3 — `legacy`: история,
   машинно не проверяются и не считаются ошибкой.
2. `actor.session` непустой и `!== issuedBy.session`, `!== executorSession`.
3. `independence.level` ≥ минимума риска; `declared` только для low.
   Если записан `actor.sourceKind`: `harness`/`runner` требуют
   `separate-session`, `ci`/`manual` — `declared`; неизвестный вид и
   расхождение с уровнем — ошибка.
4. High: `actor.kind = human`, `keyId` из `human-*`, `humanSignoff`, `securityReview`,
   активных обходов нет.
5. `acceptorRun.fresh = true` для medium/high; `redExpectation.ok = true`;
   `red.contractCommit = contractCommit`; для версии 6 — `red.baseSha = contractCommit`.
6. `task.md`/`criteria.json` в кандидатном коммите совпадают с хешами записи.
7. `acceptance.json` не входит в кандидата; metadata-коммит отличается от кандидата
   только им.
8. `verify.json`/`red.json` в кандидате совпадают с записанными хешами.
9. `decisions.digest` пересчитан по контракту кандидата; `decisions.assumed` совпадает
   с выведенным; при непустом `assumed` — `releaseReady = false`, для high — отказ.
10. Решение с `impact = user-visible | public-contract` без доказательства в записи
    недопустимо; для такого решения нужен критерий с `effect`. `accept` пишет
    `effectsRequired`, `effects` и `effectConsistency {checked, ok, mode, links}`.
    `check` пересчитывает `effectConsistency` по контракту кандидата: `ok` и `links`
    обязаны совпадать, нарушения применяются по `policy.decisions`. Записи без блока —
    до 2.4.0: не ломаются (предупреждение). Проверка `effects`/`effectConsistency`
    подчиняется `policy.decisions`; записи до 2.3.2 флага `effectsRequired` не имеют.
11. `attack.sha256` совпадает с `attack.json` в кандидате; `findings.unresolved = 0`;
    критик — не постановщик; при `policy.roles.modelFamily = fail` семейства
    приёмщика и постановщика различаются.  
    `actor.family` и `independence.modelLevel` сверяются с реестром `models`.

## 8. Слепая приёмка

1. Приёмщик получает задание, критерии, замок и репозиторий. Отчёт исполнителя **не
   читает** до прогона.
2. Фиксирует сессию (окружение), проверяет `contractCommit` и `--expect-contract`.
3. Запускает `accept` (для medium/high — он сам прогоняет `verify`).
4. Смотрит дифф, защищённые файлы, секреты, негативные случаи.
5. Только теперь читает отчёт и сравнивает с фактическим прогоном.
6. Подписывает запись; high-risk — человек своим ключом.
7. Возвращает: принято / принято с замечаниями (follow-up ID) / отклонено с причиной.

### 8.1. Разбор замечаний приёмщика

1. Замечание — не шум и не автоматический отказ: архитектор оценивает применимость
   к проекту, риск и влияние на выкатку.
2. Каждое замечание классифицируется: `blocking` (без исправления выкатывать нельзя),
   `non-blocking` (принято осознанно, причина записана) или `follow-up` (отдельная
   задача с ID).
3. Решение — окончательная приёмка или отправка на доработку — фиксируется в
   `review.json` и попадает в запись (`review`, `releaseReady`).
4. Если решение не требует заказчика, доработка начинается автоматически сразу после
   отчёта; отдельного «начинай» не ждут.
5. Пока есть `blocking` без решения, `task-accept` отказывает, а релиз не выкатывается.
   Зелёные критерии — условие приёмки, но не разрешение на выкатку.

~~~json
{
  "decision": "accepted",
  "remarks": [
    { "id": "R1", "class": "blocking", "resolution": "поправлено в candidate" },
    { "id": "R2", "class": "non-blocking", "reason": "вне объёма задачи" },
    { "id": "R3", "class": "follow-up", "followUpId": "0070" }
  ]
}
~~~

Правила машины: `decision: "rework"` — приёмки нет; `blocking` требует `resolution`;
`non-blocking` — `reason`; `follow-up` — `followUpId`. `releaseReady` вычисляется:
решение `accepted` и нет неразрешённых `blocking`.

## 9. CI

- На каждый PR: `task-lint` для изменённых заданий, `check` для изменённых записей.
- `check` получает публичные ключи из репозитория; приватных ключей в CI нет.
- Нарушение — блокирующая ошибка, а не предупреждение.
- Отдельная джоба гоняет `selftest` пакета: ворота, которые не проверяются, гниют.
- Branch protection: обязательны `lint`, `check`, `selftest`; force-push запрещён.
- **Regress по расписанию** (например, ночью): `task-regress --strict` по принятым
  заданиям, отчёт — артефакт. Долг провенанса фиксируется в `regress.baseline.json`
  (коммитится, `reviewBy` — 30 дней); новая запись с долгом, которой нет в baseline,
  валит прогон.

## 10. Ключи

- `agent-*` — ключ приёмщика-агента. Приватный — в окружении приёмщика, вне репозитория.
- `human-*` — ключ человека, для high-risk. Отдельная учётная запись/DPAPI/токен, не
  доступная агенту.
- Публичные ключи — `acceptors.json` в репозитории: `{keyId, publicKeyPem, kind, owner,
  createdAt, revokedAt}`.
- Ротация: новый `keyId`; старые публичные ключи не удаляются (записи проверяемы).
- Компрометация: `revokedAt`, запись об инциденте, повторная приёмка затронутых задач.

## 11. Модель угроз

| Угроза | Проявление | Мера | Остаточный риск |
| --- | --- | --- | --- |
| Агент берёт роль приёмщика | `--acceptor judge` из той же сессии | Аттестация сессии + отказ при совпадении | Подделка env — осознанная и видимая |
| Подделка записи | Правка `acceptance.json` | Ed25519; проверка в CI | Приватный ключ у агента — подпись не граница |
| HMAC-иллюзия | Проверяющий = подписывающий | Только Ed25519 для v4 | Legacy v3 не считается независимым |
| Подмена контракта | Переписали критерии и перезамкнули | Контрактный коммит + заморозка + `--expect-contract` | Новый коммит виден в диффе |
| Подмена проверок | Правка теста | Хеши по коммиту; защищённые пути | Ошибка в `protectedPaths` |
| Подделка доказательств | Пересказ вместо вывода | Логи в репозитории, хеши, nonce | Логи без редакции секретов |
| Prompt injection | «Инструкция» в файле | Содержимое — данные; least privilege | Модель может поддаться |
| Self-accept по невнимательности | Агент запустил accept сам | Ворота отказывают; CI красит PR | Обход через `low` + `--note` |
| Ошибочное предположение | Семантика «доставки» выбрана агентом и никем не проверена | Реестр решений, `assumed` + `releaseReady=false`, атака спецификации, подтверждение человека для user-visible | Человек подтвердил не читая |
| Непроверенный код | Файл изменён, критерия на него нет, все проверки зелёные | `covers` + сверка изменённых файлов в `verify` | Критерий «покрывает» слишком широкий путь |
| Ложный диагноз и лишние итерации | Вывод из тишины журнала; «попробуй ещё» до проверки доставки | Императивы I-29/I-30, разбор в ретро | Правило держится на дисциплине: ворота не проверяют качество диагноза |
| Гниение доказательств | Принятое задание перевыпущено без нового красного; проверка закрытой задачи сломана | I-32; сверка `red.baseSha` в `check`, гейт `task-regress` | Запуск regress — по расписанию: между прогонами регресс остаётся незамеченным |

## 12. Метрики

| Метрика | Источник | Зачем |
| --- | --- | --- |
| Доля приёмок с `separate-session`/`human` | `acceptance.json` | Реальная независимость, а не заявленная |
| Заблокированные самоприёмки | логи `accept` | Работают ли ворота |
| First-pass acceptance | записи | Качество заданий |
| Rework hours | verify fail → accept | Стоимость переделок |
| Escaped defects | после релиза | Эффективность проверок |
| Flaky rate | повторные прогоны | Стабильность |
| Criteria automation | tags | Покрытие |
| Доля решений с исполняемым доказательством | `decisions` + записи | Где семантика держится на человеке, а где на проверке |
| Релизы с `assumed` | `releaseReady=false` | Цель — 0; каждый случай — повод подтвердить решение |
| Файлы без покрытия | `verify.json.coverage.uncovered` | Дыры «код без критерия» |
| Находки атаки до замка | `attack.json` | Сколько дыр ловится до реализации, а не в приёмке |
| `blocking` без решения | `attack.findings.unresolved` | Цель — 0; каждый случай — долг перед выпуском |
| Итерации до инструментальной проверки | логи сессий, ретро | Сколько раз просили повторить до проверки |
| Доля задач с критерием эффекта | `criteria` | «Готово» по эффекту, а не по отправке |
| Регрессы закрытых заданий | `task-regress` | Гниение доказательств приёмки |

Метрики — для улучшения процесса, не для наказания.

## 13. Портируемость и адаптеры

Всё, что зависит от харнесса, — это источник идентификатора актора. С 2.6.0 это
не «два имени в коде», а настраиваемая цепочка `actor.sources` в
`workflow.config.json`: каждая запись — `{ "env": "<переменная>", "kind": "<вид>" }`.
Первый источник с непустым значением побеждает, а ВИД источника решает, чем
подтверждена сессия.

| Вид (`kind`) | Источник сессии | `attestedBy` | Уровень | Где включается |
| --- | --- | --- | --- | --- |
| `harness` | харнесс агента (DSH: `DSH_SESSION_ID`, у каждого агента свой, доходит до child-процессов) | `env` | `separate-session` | шаблон конфига, по умолчанию |
| `runner` | обёртка проекта (`WF_ACTOR_SESSION`); DSH не нужен | `env` | `separate-session` | `actor.sources` проекта |
| `ci` | идентификатор джобы (`GITHUB_RUN_ID`, `CI_JOB_ID`) | `declared` | `declared`: та же машина, medium/high закрыты | `actor.sources` |
| `manual` | значение выставил человек или скрипт (`TASK_ACTOR_SESSION`) | `declared` | `declared`: medium/high закрыты | `actor.sources` или legacy `fallbackEnv` |
| человек | ключ `human-*`, `--human <кто>` | `key` | `human` | ключ человека |
| — | окружение пустое | `none` | `declared` | — |

Модель резолвится так же: `actor.modelSources` — первый непустой, иначе
`unknown` (не «другое семейство»).

Legacy-конфиг без `sources` поведения не меняет: `primaryEnv` синтезируется как
`harness`, `fallbackEnv` — как `manual`; `primaryEnv`/`fallbackEnv`/`modelEnv`
остаются в объекте и читаются панелью. Конфиг без этих полей не падает —
дефолты подставляет нормализация.

Правило: если окружение не даёт идентификатор, ворота не выдумывают его. Запись
получает `attestedBy: declared` и уровень `declared`, допустимый только для low.
Молчаливое повышение уровня запрещено: `ci` и `manual` никогда не дают
`separate-session`, а неизвестный вид источника — ошибка конфигурации (`doctor`
красный, `task-accept` отказывает), а не разрешение.

Основание видно в записи: `actor.source` (имя переменной), `actor.sourceKind`
(вид) и `independence.basis`. `task-check-acceptance` сверяет вид с уровнем:
`harness`/`runner` требуют `separate-session`, `ci`/`manual` — `declared`;
записи до 2.6.0 без поля проверяются как раньше. Подключение конкретного
харнесса — `adapters/dsh.md` (harness), `adapters/opencode.md` и
`adapters/generic.md` (runner), `adapters/ci.md` (только проверка записей).

## 14. Антипаттерны

- Приёмка «своего» задания тем же агентом.
- `--acceptor judge` как доказательство роли.
- HMAC-ключ в общем каталоге пользователя.
- Отчёт исполнителя, прочитанный до прогона.
- Критерий «файл на месте».
- Правка теста под результат.
- Перезамок после красного.
- Запись, которую никто не проверяет.
- Логи, на которые ссылаются, но которых нет в репозитории.
- «Независимость» в тексте без механизма.
- Решение о пользовательском поведении, у которого нет ни критерия, ни человека.
- Критерий, который «покрывает» весь репозиторий, чтобы `covers` формально сошёлся.
- `assumed`, спрятанный правкой записи (ловится пересчётом digest по контракту).
- «Вывод из тишины журнала»: «записей нет, значит выключено».
- «Попробуй ещё раз» до проверки, доходят ли запросы до системы.
- «Готово = выкатил»: отправка принята за получение.
- Перевыпуск задания с переносом старой приёмки и старого красного прогона.

## 15. Внедрение

1. **Пилот на 3–5 задачах medium.** Полный цикл, замер накладных расходов.
2. **Порядок:** контракт → красный → зелёный → приёмка с аттестацией → проверка в CI.
3. **Порядок включения:** `init` → `new-task` → `hash`/`lint`/`red`/`verify` →
   `accept` с актором и Ed25519 → high-risk. Пакет уже содержит все шаги; включать их
   надо по одному, проверяя отказ самоприёмки после каждого.
4. **Правила — в репозиторий**, версионировать; один владелец спеки.
5. **Обучать постановщика**: чек-лист важнее опыта.
6. **Удалять неработающие правила**: правило без проверки заменяется проверяемым.

## Приложение B. Минимальные требования к гейтам

Гейт обязан: принимать `--task`, `--repo`; возвращать 0/1; писать артефакт в каталог
задания; не читать секреты из репозитория; не ходить в сеть без критерия про сеть.
`accept` обязан: не писать `acceptance.json` при любой ошибке; не включать запись в
кандидатный коммит; фиксировать все обходы.
