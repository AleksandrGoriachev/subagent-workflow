- Границы: до первой правки сверь список файлов, которые собираешься менять, с `allowedPaths`;
  файл вне границ — стоп и один вопрос постановщику, а не «поправлю и посмотрим»
  (0046→0054: 20 мин 30 с выброшенной работы).
- Сборка: <команда>
- Проверка кода парой контрактов (0127, 2.6.106): **`node tools/check-tests.mjs`** — отбор по изменённым
  файлам (full при `plugin/lib|test|tools`, affected при `spec/**`/`tools/**`, selftest если менялись только
  docs/артефакты). Набор тестов руками в контракте не прописывается: `node --test <файл>` допустим только как
  точечная итерация, а не как критерий приёмки. Итерации — `node spec/scripts/tests-for.mjs <изменённые пути>`.
- База/фикстуры: <команда сброса>
- Известные ловушки: <...>
- В отчёте: что гонялось — сколько раз шёл полный набор и какие точечные наборы запускались.
- Дисциплина оценки (0122, 2.6.104): ворота и тяжёлые прогоны — **только сторожем движка**:
  `node spec/scripts/gate.mjs <red|verify|accept|hash|lint|tests|selftest> [аргументы] --tail 20`.
  Он печатает id задания, строку `LOG <абсолютный путь>`, вердикт `DONE <id> exit=<код>` и хвост лога.
  Сырые `pwsh`/`run_code` с большим timeout политика отклоняет (`enforcement.waitPolicy=fail`);
  хост-инструменты `run_in_background`/`job_output` есть не у всякого узла — полагаться на них нельзя.
  Читать результат: `node spec/scripts/job.mjs log <id> [--tail N]` или `wait <id> --tail N`; лог всегда
  в `.tmp/jobs` того корня, где лежит `job.mjs` (в развёрнутой копии — `docs/subagent-workflow/.tmp/jobs`).
- До старта ворот — не больше 120 с на подготовку (окружение, чтение файлов): ворота не ждут.
- Паузы и замеры: спать в инструменте дольше политики нельзя (`Start-Sleep`/`timeoutMs` > 120 с отклоняются).
  Замер с интервалом (heartbeat, два сэмпла по 60 с) — тоже сторож:
  `node spec/scripts/job.mjs start -- node <сэмплер>`, затем `node spec/scripts/job.mjs wait <id> --tail 40`;
  результат — `job.mjs log <id>`. Это тот же вход, что у ворот, и он не требует пауз в инструменте.
- Ручной прогон критерия — не более одного и только если он идёт меньше 15 с; дольше — ждать ворота.
- Приёмщик не читает отчёт исполнителя: при risk=medium/high — только с названной причиной
  (`--report-read-reason "<зачем>"`).

## Отчёт

1. Что изменено — списком, по смыслу.
2. Файлы — полными путями.
3. Каждая проверка из `criteria.json` — команда и exit код (дословный вывод), включая регресс.
   Список берётся из контракта целиком, а не из того, что успел прогнать: непрогнанная проверка
   так и пишется — `NOT RUN`, молчаливых пропусков в отчёте нет.
4. Отклонения от задания и почему.
5. Сумма критериев, которая исполнялась.
6. `git status --short`.

## Лёгкая задача (без criteria.json)

Для внутренней задачи без исполнительного дефекта (watchdog, утилита, обслуживание) файл `criteria.json`
не нужен. В `TASK-META` вместо него объявляются наблюдаемые проверки:

```json
"risk": "low",
"mode": "light",
"checks": [
  { "id": "C1", "title": "сторож не падает за сутки", "command": "node tools/watchdog.mjs --check", "expect": { "exitCode": 0 } }
]
```

Правила лёгкой задачи:

1. `risk` только `low`: обход красного — не для medium/high.
2. `criteria.json` и `criteria.lock` не создаются; проверки заморожены контрактным коммитом (`task.md`).
3. `task-hash --write` отказывает с рецептом «замок не требуется» — это норма, не ошибка.
4. Красный не доказывается: `task-verify --allow-missing-red`, обход виден в `verify.json`.
5. Приёмка: `task-accept --allow-missing-red --note "<почему лёгкая>"` — обход требует причины.
6. Таблица «Критерии приёмки» всё равно нужна: ID совпадают с `checks`.
