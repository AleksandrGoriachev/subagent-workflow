# Плагин DSH: что он даёт и чего не должен делать

Черновик решения. Плагин **не нужен**, чтобы настроить роли: политика и модели
живут в `workflow.config.json` и проверяются воротами (2.2.0). Плагин нужен там,
где заканчивается конфигурация и начинается запуск: поднять роль нужной моделью,
дождаться результата, повторить по расписанию.

## Что уже работает без плагина

| Задача | Как решается сейчас |
| --- | --- |
| «Какая модель допустима для приёмщика/критика» | `roles` + `models` в конфиге; `task-accept` и `task-attack` сверяют `DSH_MODEL` |
| «Насколько строго проверять» | `policy`: `fail` / `warn` / `off` по каждому правилу |
| «Факт записан?» | `actor.family`, `independence.modelLevel`, `attack.*` в записи о приёмке |
| «Как запустить другую модель» | отдельная сессия или отдельный профиль DSH (`adapters/dsh.md`) |
| «Когда запускать ночной разбор» | напоминание DSH `schedule_create` |

## Что может плагин

1. **Запуск роли с моделью из конфига.** Команда вида
   `dsh workflow role critic --task docs/tasks/0042`: плагин читает
   `workflow.config.json`, создаёт **отдельную** сессию с моделью роли, вставляет
   `task-attack --prompt` и возвращает управление, когда `attack.json` появился.
   То же для приёмщика: сессия с моделью acceptor и ключом из `~/.wf-keys`.
2. **Расписание ролей.** Ночной наблюдатель и авто-атака новых заданий — тем же
   механизмом, без ручного копирования промпта.
3. **Панель настроек.** Показать и отредактировать `policy`, `roles`, `models`
   с валидацией (неизвестный уровень, модель без семейства, роль без модели).
4. **Диагностика.** Кнопка «doctor»: политика, роли, наличие ключей, модели.

## Чего плагин не должен делать

- **Не подписывает и не принимает.** Подпись — у ворот и ключа; плагин может
  только запустить сессию, в которой ворота исполнятся.
- **Не выбирает модель молча.** Если роли нужна модель, которой нет, — отказ,
  а не тихий откат на модель по умолчанию. Иначе «другой агент» превращается в
  фикцию, а запись будет утверждать обратное.
- **Не даёт агенту менять себе модель под проверку.** Модель роли фиксируется в
  момент запуска сессии и записывается в артефакты; смена модели в середине —
  новый запуск с новой записью.
- **Не хранит ключи.** Пути к ключам читаются из конфигурации и окружения, как
  сейчас; приватный ключ не попадает в состояние плагина.
- **Не обходит политику.** `off` остаётся `off`: плагин показывает, но не
  включает проверку сам.

## Чего не хватает в DSH

| Нужно | Зачем | Обходной путь |
| --- | --- | --- |
| Создание сессии с явной моделью | запуск роли «другой моделью» | отдельный профиль или ручной выбор модели |
| Параметр модели у `subagent` | критик как дочерний агент | отдельная сессия (и это правильнее) |
| Headless-запуск сессии | ночной разбор без открытого окна | напоминание в резидентную сессию |
| Событие «сессия завершилась» для плагина | дождаться `attack.json` | опрос файла |

Пункт «модель у субагента» стоит просить у DSH только если понадобится именно
дочерний агент; для независимости отдельная сессия лучше.

## Минимальный плагин (если делать)

1. Читает `workflow.config.json` (схема — та же, что у ворот).
2. Команда `role run --role critic|acceptor --task <dir>`:
   - берёт модель роли из `roles`, семейство — из `models`;
   - создаёт сессию с этой моделью (или отказывает, если DSH не умеет);
   - вставляет промпт из `task-attack --prompt` / задание приёмщику;
   - по завершении пишет в лог: роль, модель, сессия, время.
3. Команда `role list` — что настроено и что реально запускалось.
4. Ничего не пишет в репозиторий: артефакты создают сами ворота в сессии роли.

Оценка: 1–2 дня на команду запуска и список ролей, если DSH даёт создание сессии
с моделью; иначе — только GUI-панель и ручной запуск, что почти не экономит время.

## Решение

Сейчас — конфигурация и адаптер, без плагина. Плагин оправдан, когда ручной запуск
роли станет узким местом: ночной разбор + атака каждого medium/high задания — это
2–4 запуска в день, пока они укладываются в минуту внимания. Пересмотреть после
двух недель работы петли.
